# 18-1-注册并启动任务

本文基于当前项目源码分析：如果外部系统希望“通过 API 直接向某个项目注册任务并启动执行”，当前 API 是否满足，以及应如何调用。

## 一、结论

当前 API **可以满足**“注册一个任务并启动执行”的需求，但前提是把这里的“任务”建模为 **工作流定义中的任务节点**。也就是说，外部系统需要创建一个包含目标任务节点的工作流定义，再上线该工作流，最后启动工作流实例。

当前 API **不满足**以下两种形态：

| 需求形态 | 是否满足 | 说明 |
| --- | --- | --- |
| 一次 HTTP 调用完成“创建任务 + 上线 + 启动” | 不满足 | 当前没有一体化接口，需要多步调用 |
| 创建一个不属于任何工作流的普通批任务，并直接启动这个任务 | 不满足 | `TaskDefinitionController` 没有 `create` 接口，`/executors/task-instance/{code}/start` 当前实现直接抛 `Not supported` |
| 创建一个单节点工作流，把这个节点当成任务执行 | 满足 | 推荐路径：生成任务 code -> 创建工作流定义 -> 上线工作流 -> 启动工作流 |

推荐调用链：

| 顺序 | API | 作用 |
| --- | --- | --- |
| 0 | 准备 `token` 或登录 session | API 鉴权 |
| 1 | `GET /projects/{projectCode}/task-definition/gen-task-codes?genNum=1` | 生成任务 code |
| 2 | `POST /projects/{projectCode}/workflow-definition` | 注册工作流定义，同时保存任务定义和任务关系 |
| 3 | `POST /projects/{projectCode}/workflow-definition/{code}/release` | 上线工作流 |
| 4 | `POST /projects/{projectCode}/executors/start-workflow-instance` | 启动执行，返回工作流实例 ID |

实际访问时需要加 context path。默认配置是：

```text
http://<api-host>:12345/gyyun
```

例如表中的 `/projects/{projectCode}/workflow-definition`，实际路径是 `/gyyun/projects/{projectCode}/workflow-definition`。

## 二、源码依据

### 1. API 基础路径和鉴权

`gyyun-api/src/main/resources/application.yaml` 配置：

| 配置 | 值 |
| --- | --- |
| `server.port` | `12345` |
| `server.servlet.context-path` | `/gyyun/` |

`LoginHandlerInterceptor` 的认证顺序是：

| 顺序 | 逻辑 |
| --- | --- |
| 1 | 先读请求头 `token` |
| 2 | 如果有 `token`，按 `t_ds_access_token` 查询用户且要求未过期 |
| 3 | 如果没有 `token`，再走登录 session |
| 4 | 校验成功后把当前用户写入 `Constants.SESSION_USER` |

因此，外部系统调用推荐使用请求头：

```text
token: <access-token>
```

Token 可以通过 `/access-tokens` 创建，但创建 token 本身需要已有登录态或已有 token 权限。生产对接时通常由管理员预先创建一个专用 API 用户和 access token。

### 2. 创建工作流会同时保存任务

`WorkflowDefinitionController` 提供：

```text
POST /projects/{projectCode}/workflow-definition
```

该接口接收：

| 参数 | 说明 |
| --- | --- |
| `name` | 工作流定义名称 |
| `description` | 描述 |
| `globalParams` | 全局参数 JSON 字符串，默认 `[]` |
| `locations` | DAG 布局 JSON 字符串，可为空 |
| `timeout` | 工作流超时时间 |
| `taskRelationJson` | 任务依赖关系 JSON 字符串 |
| `taskDefinitionJson` | 任务定义 JSON 字符串 |
| `executionType` | 工作流执行类型，默认 `PARALLEL` |

实现层 `WorkflowDefinitionServiceImpl.createWorkflowDefinition` 会做三件事：

| 步骤 | 源码行为 |
| --- | --- |
| 1 | `generateTaskDefinitionList(taskDefinitionJson)` 解析并校验任务定义 |
| 2 | `generateTaskRelationList(taskRelationJson, taskDefinitionLogs)` 解析并校验任务关系、DAG 是否有环 |
| 3 | `createDagDefine(...)` 保存任务定义、工作流定义、任务关系 |

`createDagDefine` 内部依次调用：

| 调用 | 作用 |
| --- | --- |
| `processService.saveTaskDefine(...)` | 写入 `t_ds_task_definition` 和 `t_ds_task_definition_log` |
| `processService.saveWorkflowDefine(...)` | 写入 `t_ds_workflow_definition` 和 `t_ds_workflow_definition_log` |
| `processService.saveTaskRelation(...)` | 写入 `t_ds_workflow_task_relation` 和日志表 |

所以，当前项目的“注册任务”入口并不是单独的 `POST /task-definition`，而是创建工作流定义时一起提交 `taskDefinitionJson`。

### 3. 创建后默认是下线状态

`ProcessServiceImpl.saveWorkflowDefine` 在从工作流定义入口保存时，如果原定义不是 `ONLINE`，会把版本保存为 `OFFLINE`。

新建工作流的 `WorkflowDefinition` 构造函数没有设置 `releaseState`，所以新建后默认是 `OFFLINE`。这意味着创建成功后不能立刻调用启动接口，必须先上线：

```text
POST /projects/{projectCode}/workflow-definition/{workflowDefinitionCode}/release
releaseState=ONLINE
```

`ExecutorServiceImpl.triggerWorkflowDefinition` 和 `TriggerWorkflowDTOValidator` 都会检查工作流是否在线。工作流未上线时会被拒绝。

### 4. 启动会通过 master RPC 创建实例和命令

`ExecutorController` 提供：

```text
POST /projects/{projectCode}/executors/start-workflow-instance
```

`START_PROCESS` 分支会构造 `WorkflowTriggerRequest`，再调用 `ExecutorServiceImpl.triggerWorkflowDefinition`。实现层校验项目权限、工作流归属、工作流上线状态后，通过 `TriggerWorkflowExecutorDelegate` 从注册中心选择一个 master，并 RPC 调用 master 的 `manualTriggerWorkflow`。

master 侧 `WorkflowManualTrigger` 会：

| 步骤 | 行为 |
| --- | --- |
| 1 | 按工作流 code/version 查询工作流定义日志 |
| 2 | 创建 `WorkflowInstance`，初始状态为 `SUBMITTED_SUCCESS` |
| 3 | 构造 `CommandType.START_PROCESS` 命令 |
| 4 | 并行工作流写入命令表；串行工作流写入串行命令表 |
| 5 | 返回 `workflowInstanceId` |

所以启动接口要求 master 服务在线并已注册，否则会报 `no master server available`。

### 5. 单任务启动接口当前不可用

`ExecutorController` 中存在：

```text
POST /projects/{projectCode}/executors/task-instance/{code}/start
```

但它对应的 service 方法是 `execStreamTaskInstance`，当前 `ExecutorServiceImpl.execStreamTaskInstance` 直接：

```java
throw new ServiceException("Not supported");
```

因此不能把它当作普通批任务的独立启动接口使用。

## 三、推荐调用流程

下面示例注册一个单节点 `SHELL` 任务，并立即启动执行。

### 0. 准备变量

```bash
BASE="http://127.0.0.1:12345/gyyun"
TOKEN="<your-access-token>"
PROJECT_CODE="<target-project-code>"
WORKFLOW_NAME="api_shell_demo_$(date +%s)"
```

说明：

| 变量 | 说明 |
| --- | --- |
| `PROJECT_CODE` | 目标项目 code，不是项目数据库自增 id |
| `TOKEN` | 请求头 access token |
| `WORKFLOW_NAME` | 工作流定义名，同一项目内必须唯一 |

### 1. 生成任务 code

```bash
TASK_CODE=$(
  curl -sS \
    -H "token: ${TOKEN}" \
    "${BASE}/projects/${PROJECT_CODE}/task-definition/gen-task-codes?genNum=1" \
  | jq -r '.data[0]'
)

echo "${TASK_CODE}"
```

必须提前有任务 code，因为 `taskRelationJson.postTaskCode` 不能为 `0`，并且必须能和 `taskDefinitionJson[].code` 对上。

### 2. 拼接任务定义和任务关系

```bash
TASK_DEFINITION_JSON=$(
  jq -cn --argjson code "${TASK_CODE}" '
  [
    {
      code: $code,
      name: "shell_task",
      version: 0,
      description: "",
      delayTime: 0,
      taskType: "SHELL",
      taskParams: {
        localParams: [],
        rawScript: "echo '\''hello from api'\''",
        resourceList: []
      },
      flag: "YES",
      taskPriority: "MEDIUM",
      workerGroup: "default",
      environmentCode: -1,
      failRetryTimes: 0,
      failRetryInterval: 1,
      timeoutFlag: "CLOSE",
      timeoutNotifyStrategy: "",
      timeout: 0,
      taskGroupId: 0,
      taskGroupPriority: 0,
      cpuQuota: -1,
      memoryMax: -1,
      taskExecuteType: "BATCH"
    }
  ]')

TASK_RELATION_JSON=$(
  jq -cn --argjson code "${TASK_CODE}" '
  [
    {
      name: "",
      preTaskCode: 0,
      preTaskVersion: 0,
      postTaskCode: $code,
      postTaskVersion: 0,
      conditionType: "NONE",
      conditionParams: {}
    }
  ]')
```

单节点工作流的关系规则：

| 字段 | 值 |
| --- | --- |
| `preTaskCode` | `0`，表示没有上游 |
| `postTaskCode` | 当前任务 code |
| `conditionType` | `NONE` |
| `conditionParams` | `{}` |

多节点时，需要为每个节点生成 code，并按边关系设置 `preTaskCode -> postTaskCode`。

### 3. 创建工作流定义

```bash
CREATE_RESULT=$(
  curl -sS -X POST \
    -H "token: ${TOKEN}" \
    -H "Content-Type: application/x-www-form-urlencoded" \
    --data-urlencode "name=${WORKFLOW_NAME}" \
    --data-urlencode "description=created by external api" \
    --data-urlencode "globalParams=[]" \
    --data-urlencode "locations=[]" \
    --data-urlencode "timeout=0" \
    --data-urlencode "executionType=PARALLEL" \
    --data-urlencode "taskDefinitionJson=${TASK_DEFINITION_JSON}" \
    --data-urlencode "taskRelationJson=${TASK_RELATION_JSON}" \
    "${BASE}/projects/${PROJECT_CODE}/workflow-definition"
)

echo "${CREATE_RESULT}" | jq .
WORKFLOW_CODE=$(echo "${CREATE_RESULT}" | jq -r '.data.code')
```

注意：

| 点 | 说明 |
| --- | --- |
| 请求体 | 这里是表单参数，不是 JSON body，因为 Controller 用的是 `@RequestParam` |
| `taskDefinitionJson` | 表单字段值是 JSON 字符串 |
| `globalParams` | 表单字段值是 JSON 字符串 |
| 返回值 | 成功时 `code=0`，`data.code` 是工作流定义 code |
| 上线状态 | 创建成功后仍是 `OFFLINE` |

### 4. 上线工作流定义

```bash
curl -sS -X POST \
  -H "token: ${TOKEN}" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "releaseState=ONLINE" \
  "${BASE}/projects/${PROJECT_CODE}/workflow-definition/${WORKFLOW_CODE}/release" \
| jq .
```

上线时会校验：

| 校验 | 说明 |
| --- | --- |
| 项目权限 | 调用用户需要有项目操作权限 |
| 工作流存在 | 工作流 code 必须存在 |
| DAG 合法 | 任务关系必须合法 |
| 子工作流 | 如果包含子工作流，子工作流也必须在线 |

### 5. 启动工作流实例

```bash
NOW="$(date '+%F %T')"

START_RESULT=$(
  curl -sS -X POST \
    -H "token: ${TOKEN}" \
    -H "Content-Type: application/x-www-form-urlencoded" \
    --data-urlencode "workflowDefinitionCode=${WORKFLOW_CODE}" \
    --data-urlencode "scheduleTime=${NOW},${NOW}" \
    --data-urlencode "failureStrategy=END" \
    --data-urlencode "startNodeList=" \
    --data-urlencode "taskDependType=TASK_POST" \
    --data-urlencode "execType=START_PROCESS" \
    --data-urlencode "warningType=NONE" \
    --data-urlencode "warningGroupId=0" \
    --data-urlencode "workflowInstancePriority=MEDIUM" \
    --data-urlencode "workerGroup=default" \
    --data-urlencode "tenantCode=default" \
    --data-urlencode "environmentCode=-1" \
    --data-urlencode "dryRun=0" \
    "${BASE}/projects/${PROJECT_CODE}/executors/start-workflow-instance"
)

echo "${START_RESULT}" | jq .
WORKFLOW_INSTANCE_ID=$(echo "${START_RESULT}" | jq -r '.data[0]')
```

成功时返回类似：

```json
{
  "code": 0,
  "msg": "success",
  "data": [123]
}
```

其中 `data[0]` 是新创建的工作流实例 ID。

参数说明：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `workflowDefinitionCode` | 创建接口返回的 `data.code` | 必填 |
| `scheduleTime` | `当前时间,当前时间` | Controller 标记为必填；`START_PROCESS` 分支当前没有实际使用它 |
| `failureStrategy` | `END` 或 `CONTINUE` | 失败策略 |
| `startNodeList` | 空 | 空表示按整个 DAG 正常执行；指定任务 code 可从指定节点启动 |
| `taskDependType` | `TASK_POST` | 执行下游依赖 |
| `execType` | `START_PROCESS` | 普通手动启动 |
| `warningType` | `NONE` | 不告警 |
| `tenantCode` | 实际租户编码 | 必须存在；默认示例用 `default` |
| `workerGroup` | 实际 worker group | 默认示例用 `default` |
| `environmentCode` | `-1` | 默认环境 |
| `dryRun` | `0` | `0` 表示真实运行 |

## 四、常见问题和限制

### 1. 为什么不直接调用 TaskDefinitionController？

`TaskDefinitionController` 当前提供的是更新、版本切换、详情、生成任务 code、上下线任务定义等接口，没有 `POST /task-definition` 创建接口。

创建任务定义的实际入口在 `WorkflowDefinitionServiceImpl.createWorkflowDefinition` 中，通过 `taskDefinitionJson` 随工作流一起保存。

### 2. 创建后能否直接启动？

不能。创建后工作流默认是 `OFFLINE`，启动接口校验工作流必须是 `ONLINE`。必须先调用 release 接口上线。

### 3. 能否只启动某个任务节点？

有两种情况：

| 场景 | 是否可行 |
| --- | --- |
| 新注册一个单节点工作流，并启动整个工作流 | 可行，推荐 |
| 对已有已完成工作流实例执行某个任务节点 | 可通过 `/executors/execute-task`，但它依赖已有工作流实例，不能用于首次注册并启动 |
| 直接启动一个普通批任务定义 | 当前不可行，`/executors/task-instance/{code}/start` 未实现 |

### 4. 为什么要先生成任务 code？

创建接口会先校验 `taskRelationJson`，要求 `postTaskCode` 非 0 且能在 `taskDefinitionJson` 中找到对应任务。虽然底层 `saveTaskDefine` 对 code 为 0 的任务定义有自动生成逻辑，但任务关系校验发生在保存之前，因此外部调用应先通过 `gen-task-codes` 生成 code。

### 5. 请求能否用 JSON body？

当前这些接口大多使用 `@RequestParam`，应使用 `application/x-www-form-urlencoded` 表单提交。JSON 数组/对象作为某个表单字段的字符串传入，例如 `taskDefinitionJson=<json-string>`。

### 6. 外部调用需要哪些权限？

调用 token 对应的用户至少需要：

| 操作 | 权限要求 |
| --- | --- |
| 生成任务 code | 已登录用户即可进入接口，但实际项目链路建议使用项目成员或管理员 |
| 创建工作流定义 | 目标项目写权限 |
| 上线工作流定义 | 工作流上线/下线权限 |
| 启动工作流 | 执行权限，对应源码里的 `project:executors:execute` |

如果是普通用户，还要确认已经被授权到目标项目。

### 7. 需要哪些运行时组件？

启动接口不只依赖 API Server，还依赖：

| 组件 | 原因 |
| --- | --- |
| Registry | API 通过注册中心选择 master |
| Master | 接收 `manualTriggerWorkflow` RPC，创建实例和命令 |
| Worker | 实际执行任务插件 |
| Metadata DB | 保存工作流定义、实例、命令、任务实例等数据 |

没有 master 在线时，启动会失败并提示 `no master server available`。

## 五、最终判断

对“通过 API 向某个项目注册任务并启动执行”这个需求，当前项目 API 的结论是：

| 判断 | 内容 |
| --- | --- |
| 是否可做 | 可以 |
| 推荐实现 | 创建一个单节点或多节点工作流定义，把任务作为工作流节点提交 |
| 是否单接口 | 不是，需要至少生成 code、创建、上线、启动几步 |
| 是否支持独立普通任务启动 | 不支持 |
| 是否需要改源码 | 如果接受“任务 = 工作流节点”，不需要改源码；如果必须要单接口或独立任务模型，需要新增聚合 API 或补齐独立任务创建/启动实现 |

如果要给外部系统提供更简洁的对接面，建议在 `gyyun-api` 新增一个聚合接口，例如：

```text
POST /projects/{projectCode}/external-tasks/register-and-start
```

该接口内部顺序执行：

| 内部步骤 | 说明 |
| --- | --- |
| 1 | 生成任务 code |
| 2 | 组装单节点工作流定义 |
| 3 | 调用现有创建逻辑保存工作流、任务、关系 |
| 4 | 调用上线逻辑 |
| 5 | 调用启动逻辑 |
| 6 | 返回 `workflowDefinitionCode`、`taskCode`、`workflowInstanceId` |

这样可以复用当前成熟的工作流执行链路，同时给外部调用方一个真正的“一步注册并启动”接口。
