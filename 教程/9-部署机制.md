# 9-部署机制

本文档根据当前项目的部署脚本、Dockerfile、Docker Compose、Helm Chart、Terraform、各服务启动类、配置文件和官方安装文档整理，说明 DolphinScheduler 采用的快速部署机制、每个服务的职能、前后依赖关系和部署注意事项。

## 一、结论总览

当前项目不是只有一种部署方式，而是提供了多层次的快速部署机制：

| 部署机制                  | 入口文件/目录                                                                                                                            | 适用场景                                | 核心特点                                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Standalone 极速体验       | `standalone-server/bin/start.sh`、`StandaloneServer`、`standalone-server.dockerfile`                                               | 新手体验、功能演示、少量工作流          | API、Master、Worker、Alert 在一个 JVM 进程中运行；默认 H2 内存数据库和 JDBC Registry；最少外部依赖                                   |
| 二进制包伪集群/单机多进程 | `gyyun-dist`、`bin/gyyun-daemon.sh`、各服务 `bin/start.sh`                                                                         | 单机完整体验、小规模使用、离线部署      | API/Master/Worker/Alert 分进程运行；依赖外部数据库和注册中心；用守护脚本启停单个服务                                                 |
| Docker Standalone         | `standalone-server.dockerfile`                                                                                                         | Docker 快速试用                         | 一个容器启动 Standalone Server，暴露 API/UI 端口                                                                                     |
| Docker Compose            | `deploy/docker/docker-compose.yml`、`.env`                                                                                           | 容器化快速体验、小中规模日常试用        | 自动拉起 PostgreSQL、ZooKeeper、API、Master、Worker、Alert；schema 初始化可单独通过 profile 执行                                     |
| 单服务 Docker 镜像        | `api-server.dockerfile`、`master-server.dockerfile`、`worker-server.dockerfile`、`alert-server.dockerfile`、`tools.dockerfile` | 复用已有数据库/注册中心、按服务拆分部署 | 每个服务独立镜像；通过环境变量覆盖数据库、注册中心和时区等配置                                                                       |
| Helm / Kubernetes         | `deploy/kubernetes/gyyun`                                                                                                              | Kubernetes 集群、生产化快速部署         | Helm Chart 管理 API Deployment、Master/Worker StatefulSet、Alert Deployment、数据库初始化 Job、ConfigMap、Secret、Service、PVC、探针 |
| Terraform / AWS           | `deploy/terraform/aws`                                                                                                                 | AWS 云上自动化搭建                      | Packer 构建 AMI，Terraform 创建 VPC、EC2、RDS、S3、ZooKeeper 等资源                                                                  |

最推荐的理解方式：

| 目标                                   | 推荐机制                                    |
| -------------------------------------- | ------------------------------------------- |
| 只想最快看到 UI 和基本工作流           | Standalone 或 standalone-server Docker 镜像 |
| 想在单机体验真实的多服务架构           | 二进制包伪集群或 Docker Compose             |
| 想用容器快速跑全套依赖                 | Docker Compose                              |
| 已有数据库和注册中心，只想启动 DS 服务 | 单服务 Docker 镜像或二进制单服务脚本        |
| 生产环境或需要弹性扩缩容               | Helm / Kubernetes                           |
| AWS 上自动创建基础设施                 | Terraform / AWS                             |

## 二、源码打包和镜像构建机制

### 1. Maven 多模块打包

项目根 `pom.xml` 是 Maven 多模块工程，部署产物由 `gyyun-dist` 汇总。

| 模块                               | 在部署中的作用                                |
| ---------------------------------- | --------------------------------------------- |
| `gyyun-api`                      | 生成 `api-server` 运行目录                  |
| `gyyun-master`                   | 生成 `master-server` 运行目录               |
| `gyyun-worker`                   | 生成 `worker-server` 运行目录               |
| `gyyun-alert/gyyun-alert-server` | 生成 `alert-server` 运行目录                |
| `gyyun-standalone-server`        | 生成 `standalone-server` 运行目录           |
| `gyyun-tools`                    | 生成 `tools` 目录，用于初始化/升级数据库    |
| `gyyun-ui`                       | 构建前端静态资源，打入二进制包的 `ui` 目录  |
| `gyyun-*-plugin`                 | 生成 shade 插件包，放入 `plugins/*-plugins` |

`gyyun-dist/src/main/assembly/gyyun-bin.xml` 会把以下内容打入 `apache-gyyun-*-bin.tar.gz`：

| 输出目录                       | 内容                        |
| ------------------------------ | --------------------------- |
| `api-server`                 | API 服务脚本、配置、依赖    |
| `master-server`              | Master 服务脚本、配置、依赖 |
| `worker-server`              | Worker 服务脚本、配置、依赖 |
| `alert-server`               | Alert 服务脚本、配置、依赖  |
| `standalone-server`          | 单机模式脚本、配置、依赖    |
| `tools`                      | 数据库初始化/升级工具和 SQL |
| `plugins/alert-plugins`      | 告警插件 shade jar          |
| `plugins/datasource-plugins` | 数据源插件 shade jar        |
| `plugins/task-plugins`       | 任务插件 shade jar          |
| `plugins/storage-plugins`    | 存储插件 shade jar          |
| `ui`                         | 前端构建产物                |
| `bin`                        | 顶层守护脚本和插件安装脚本  |
| `conf`                       | 顶层公共配置，如插件清单    |

### 2. 插件装配机制

`gyyun-dist/src/main/assembly/assembly-plugins.sh` 会在二进制包生成后做二次整理：

| 动作                               | 说明                                                                |
| ---------------------------------- | ------------------------------------------------------------------- |
| 解压 `apache-gyyun-*-bin.tar.gz` | 在 `target` 下临时展开发布包                                      |
| 整理插件 jar                       | 把插件子目录中的 `*-shade.jar` 移到 `plugins/<type>-plugins` 下 |
| 合并共享依赖                       | 把各服务 `libs/*.jar` 移到顶层 `libs`，服务目录下创建符号链接   |
| Standalone SQL 链接                | 给 `standalone-server` 创建到 `tools/sql/sql` 的符号链接        |
| 重新打包                           | 重新生成二进制 tar.gz                                               |

如果 `build.plugins.skip=true`，脚本会清空 `plugins` 目录；这会导致运行时缺少任务/数据源/存储/告警插件，需要后续通过 `bin/install-plugins.sh` 安装。

### 3. Docker 镜像构建机制

`gyyun-dist/src/main/docker/docker-build.sh` 会基于同一个二进制包构建 6 个镜像：

| 镜像                        | Dockerfile                       | 启动命令                                                                 |
| --------------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| `gyyun-api`               | `api-server.dockerfile`        | `/opt/gyyun/api-server/bin/start.sh`                                   |
| `gyyun-master`            | `master-server.dockerfile`     | `/opt/gyyun/master-server/bin/start.sh`                                |
| `gyyun-worker`            | `worker-server.dockerfile`     | `/opt/gyyun/worker-server/bin/start.sh`                                |
| `gyyun-alert-server`      | `alert-server.dockerfile`      | `/opt/gyyun/alert-server/bin/start.sh`                                 |
| `gyyun-standalone-server` | `standalone-server.dockerfile` | `/opt/gyyun/standalone-server/bin/start.sh`                            |
| `gyyun-tools`             | `tools.dockerfile`             | `ENTRYPOINT ["/bin/bash"]`，常用于执行 `tools/bin/upgrade-schema.sh` |

所有 Dockerfile 都基于 `eclipse-temurin:8-jdk`，设置：

| 环境变量                             | 作用                                  |
| ------------------------------------ | ------------------------------------- |
| `DOCKER=true`                      | 启动脚本据此追加 Docker 相关 JVM 参数 |
| `TZ=Asia/Shanghai`                 | 容器默认时区                          |
| `DOLPHINSCHEDULER_HOME=/opt/gyyun` | DS 安装目录                           |

## 四、前后依赖关系

### 1. 总体依赖图

```text
数据库(PostgreSQL/MySQL/H2)
  |
  +-- Tools 初始化/升级 Schema
  |
  +-- API Server 读写元数据、会话、资源、数据源、工作流定义
  |
  +-- Master Server 消费命令、写工作流/任务实例、Quartz JobStore
  |
  +-- Alert Server 拉取告警事件、写告警状态

注册中心(ZooKeeper/Etcd/JDBC Registry)
  |
  +-- API 查询 Master/Worker/Alert 节点
  +-- Master 注册心跳、监听 Worker、HA 选主、故障转移锁
  +-- Worker 注册心跳、被 Master 发现
  +-- Alert 注册心跳、HA 选主

API Server
  |
  +-- Netty RPC -> Master Server：工作流控制
  +-- Netty RPC -> Alert Server：测试告警/发送告警
  +-- Netty RPC -> Worker/Master：读取日志

Master Server
  |
  +-- Quartz -> 到点触发工作流
  +-- Netty RPC -> Worker Server：派发/停止/接管任务
  +-- Netty RPC -> Alert Server：发送告警

Worker Server
  |
  +-- Storage -> 下载资源和依赖
  +-- Task Plugin -> 调用 Shell/SQL/Spark/Flink/K8s/DataX/云服务等外部系统
```

### 2. 启动顺序依赖

推荐启动顺序：

| 顺序 | 组件                     | 原因                                                               |
| ---- | ------------------------ | ------------------------------------------------------------------ |
| 1    | 数据库                   | Tools、API、Master、Alert 都需要元数据库；Quartz 也依赖数据库表    |
| 2    | 注册中心                 | API/Master/Worker/Alert 需要注册、发现和 HA                        |
| 3    | Tools 初始化/升级 Schema | 第一次部署或版本升级前必须执行                                     |
| 4    | Master Server            | 先启动调度核心和 RPC 服务                                          |
| 5    | Worker Server            | 注册后可被 Master 发现并接收任务                                   |
| 6    | Alert Server             | 注册并参与告警 HA，准备消费告警                                    |
| 7    | API Server               | 对用户开放 UI/API；API 可以稍后启动，不影响已有 Master/Worker 心跳 |

实际 Docker Compose 中的启动依赖稍微宽松：

| 服务                         | Compose `depends_on` |
| ---------------------------- | ---------------------- |
| `gyyun-schema-initializer` | 等 PostgreSQL healthy  |
| `gyyun-api`                | 等 ZooKeeper healthy   |
| `gyyun-master`             | 等 ZooKeeper healthy   |
| `gyyun-worker`             | 等 ZooKeeper healthy   |
| `gyyun-alert`              | 等 ZooKeeper healthy   |

注意：Compose 的 `all` profile 只声明 API/Master/Worker/Alert 依赖 ZooKeeper，没有显式等待 PostgreSQL 和 schema initializer。实际使用时，第一次部署应先执行 `docker-compose --profile schema up -d` 初始化数据库，再执行 `docker-compose --profile all up -d`。

### 3. 运行时调用依赖

| 调用方     | 被依赖方      | 调用方式                        | 场景                                         |
| ---------- | ------------- | ------------------------------- | -------------------------------------------- |
| 前端 UI    | API Server    | HTTP                            | 页面登录、项目管理、工作流操作               |

| API Server | Alert         | Netty RPC                       | 发送测试告警                                 |

| Worker     | 存储系统      | Storage SPI                     | 下载资源、上传/拉取远程日志                  |

| Alert      | 注册中心      | Registry API                    | Alert HA                                     |

## 五、快速部署方式详解

### 1. Standalone 极速体验

二进制包方式：

```shell
tar -xvzf apache-gyyun-*-bin.tar.gz
chmod -R 755 apache-gyyun-*-bin
cd apache-gyyun-*-bin
bash ./bin/gyyun-daemon.sh start standalone-server
```

Docker 方式：

```shell
docker run --name gyyun-standalone-server \
  -p 12345:12345 \
  -p 25333:25333 \
  -d apache/gyyun-standalone-server:<version>
```

访问：

| 项       | 内容                                |
| -------- | ----------------------------------- |
| UI       | `http://localhost:12345/gyyun/ui` |
| 默认用户 | `admin`                           |
| 默认密码 | `gyyun123`                        |

启动机制：

| 步骤 | 说明                                                                           |
| ---- | ------------------------------------------------------------------------------ |
| 1    | `bin/gyyun-daemon.sh start standalone-server` 创建日志目录和 pid 文件        |
| 2    | 守护脚本调用 `standalone-server/bin/start.sh`                                |
| 3    | `start.sh` 默认 `DATABASE=h2`，拼接 API/Master/Worker/Alert/插件 classpath |
| 4    | Java 启动 `StandaloneServer`                                                 |
| 5    | Spring Boot 读取 `standalone-server/conf/application.yaml`                   |
| 6    | H2 内存库加载 schema，JDBC Registry 生效，组合服务启动                         |

注意事项：

| 注意事项                | 说明                                                          |
| ----------------------- | ------------------------------------------------------------- |
| 不建议生产使用          | 单进程、内存数据库、无真实高可用                              |
| 数据默认不持久          | 停止或重启后 H2 内存数据清空                                  |
| 可切外部数据库          | 需要改 Standalone 数据库配置并初始化数据库                    |
| 资源默认本地路径        | 默认 `/tmp/gyyun`，分布式场景需要共享存储或外部存储         |
| Python Gateway 默认关闭 | 如需 Python Gateway，修改 `api.python-gateway.enabled=true` |

### 2. 二进制包伪集群/多进程部署

二进制包部署把服务拆成多个进程，但可以部署在同一台机器。

典型流程：

| 步骤 | 命令/动作                                                                       |
| ---- | ------------------------------------------------------------------------------- |
| 1    | 安装 JDK，配置 `JAVA_HOME`                                                    |
| 2    | 准备 PostgreSQL/MySQL 和 ZooKeeper/Etcd/JDBC Registry                           |
| 3    | 解压 `apache-gyyun-*-bin.tar.gz`                                              |
| 4    | 按需执行 `bash ./bin/install-plugins.sh <version>` 下载插件                   |
| 5    | 修改 `bin/env/gyyun_env.sh` 和各服务 `conf/application.yaml`                |
| 6    | 执行 `bash tools/bin/upgrade-schema.sh` 初始化/升级数据库                     |
| 7    | 分别启动 `api-server`、`master-server`、`worker-server`、`alert-server` |

启停命令：

```shell
bash ./bin/gyyun-daemon.sh start api-server
bash ./bin/gyyun-daemon.sh start master-server
bash ./bin/gyyun-daemon.sh start worker-server
bash ./bin/gyyun-daemon.sh start alert-server

bash ./bin/gyyun-daemon.sh status api-server
bash ./bin/gyyun-daemon.sh stop worker-server
```

`gyyun-daemon.sh` 机制：

| 能力     | 说明                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 支持服务 | `api-server`、`master-server`、`worker-server`、`alert-server`、`standalone-server` |
| 支持动作 | `start`、`stop`、`status`                                                               |
| 日志目录 | `<service>/logs`                                                                            |
| pid 文件 | `<service>/pid`                                                                             |
| 启动方式 | `nohup /bin/bash <service>/bin/start.sh > <service>/logs/<service>-<hostname>.out 2>&1 &`   |
| 停止方式 | 先 `pkill -P <pid>`，等待 `STOP_TIMEOUT=5` 秒，不退出再 `pkill -P -9`                   |
| 环境覆盖 | 如果存在 `bin/env/gyyun_env.sh`，启动前会复制覆盖 `<service>/conf/gyyun_env.sh`           |

当前仓库注意点：

| 点                                 | 说明                                                                                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 有单服务守护脚本                   | 当前源码存在 `script/gyyun-daemon.sh`                                                                                         |
| 有插件安装脚本                     | 当前源码存在 `script/install-plugins.sh`                                                                                      |
| 没看到传统一键集群脚本             | 当前源码目录下未发现 `install_env.sh`、`start-all.sh`、`stop-all.sh` 这类脚本；如使用旧文档，需要以当前发布包实际内容为准 |
| `script/env/gyyun_env.sh` 很精简 | 当前源码中的默认 env 文件主要保留 AOP/ApplicationId 相关示例，实际发布包或文档中的 env 内容可能由构建/发行流程补齐              |

## 七、部署注意事项

### 1. 数据库注意事项

| 注意事项              | 说明                                                                              |
| --------------------- | --------------------------------------------------------------------------------- |
| 先初始化 schema       | 第一次部署必须运行 `tools/bin/upgrade-schema.sh` 或 Helm/Compose 对应初始化 Job |
| 升级前备份数据库      | `upgrade-schema.sh` 会执行升级 SQL，生产升级前必须备份                          |
| PostgreSQL 是默认路径 | 源码和 Helm 默认 profile 是 PostgreSQL                                            |
| MySQL 需要驱动        | 由于许可证原因，MySQL JDBC Driver 可能需要手动加入所有服务和 Tools                |
| Quartz 表也在元数据库 | Master 定时调度依赖 `QRTZ_` 表，数据库异常会影响定时触发                        |
| Standalone H2 不持久  | 默认 H2 内存库停止即丢数据                                                        |

### 2. 注册中心注意事项

| 注意事项                      | 说明                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| ZooKeeper 是默认注册中心      | API/Master/Worker/Alert 默认配置 `registry.type=zookeeper` |
| 注册中心影响服务发现          | Worker 注册不上，Master 就无法派发任务                       |
| 注册中心影响 HA               | Master Leader、Alert Active、故障转移锁都依赖 Registry       |
| Etcd/JDBC 可替换              | Helm 和 registry 插件支持 Etcd/JDBC Registry                 |
| Standalone 默认 JDBC Registry | Standalone 默认不要求外部 ZooKeeper                          |

### 3. 端口注意事项

| 服务               | 端口      | 作用                                     |
| ------------------ | --------- | ---------------------------------------- |
| API                | `12345` | HTTP/UI/REST/Actuator，路径带 `/gyyun` |
| API Python Gateway | `25333` | Python Gateway Server，默认关闭          |
| Master RPC         | `5678`  | Netty RPC                                |
| Master HTTP        | `5679`  | Actuator                                 |
| Worker RPC         | `1234`  | Netty RPC                                |
| Worker HTTP        | `1235`  | Actuator                                 |
| Alert RPC          | `50052` | Netty RPC                                |
| Alert HTTP         | `50053` | Actuator                                 |
| ZooKeeper          | `2181`  | 注册中心                                 |
| PostgreSQL         | `5432`  | 元数据库                                 |
| MySQL              | `3306`  | 元数据库可选                             |
| MinIO              | `9000`  | Helm 演示对象存储                        |

注意：源码中的部分 Dockerfile 都 `EXPOSE 12345 25333`，这并不代表 Master/Worker/Alert 实际只用这些端口；实际端口以各服务 `application.yaml` 为准。

### 4. 插件和外部依赖注意事项

| 注意事项                             | 说明                                                                               |
| ------------------------------------ | ---------------------------------------------------------------------------------- |
| 3.3.0 后二进制包可能不含完整插件依赖 | 可用 `bin/install-plugins.sh <version>` 按 `conf/plugins_config` 下载          |
| 插件 jar 不等于外部系统已安装        | Spark/Flink/Hadoop/DataX/Sqoop 等任务仍需要对应运行环境                            |
| 数据源插件可能缺 JDBC Driver         | MySQL、Oracle 等驱动可能因许可证或分发原因需要手动放入 libs                        |
| API 和 Worker 都要配置资源存储       | 只配置 API 能上传资源，但 Worker 不一定能执行依赖资源                              |
| HDFS HA 需要配置文件                 | NameNode HA 时需要把 `core-site.xml`、`hdfs-site.xml` 放到 API/Worker 配置目录 |
| 本地资源存储不适合多机               | `LOCAL` 只适合单机或共享挂载目录，多机建议 HDFS/S3/OSS 等                        |

### 5. Linux 用户和权限注意事项

| 注意事项                    | 说明                                                     |
| --------------------------- | -------------------------------------------------------- |
| Worker 多租户依赖 sudo      | 任务执行会使用 `sudo -u {tenant}` 切换用户             |
| 部署用户需免密 sudo         | 生产/伪集群应给部署用户配置 sudo 免密                    |
| `requiretty` 可能影响任务 | `/etc/sudoers` 中 `Defaults requiretty` 需要注释     |
| 目录权限要正确              | 解压目录、日志目录、资源目录、执行目录需要部署用户可读写 |
| 容器中也安装 sudo           | Dockerfile 安装了 `sudo`，用于支持任务多租户执行       |

### 6. Docker/Compose 注意事项

| 注意事项                  | 说明                                                                            |
| ------------------------- | ------------------------------------------------------------------------------- |
| Compose 建议至少 4GB 内存 | 官方文档建议给 Docker 分配足够内存                                              |
| 先 schema 后 all          | 首次部署建议先 `--profile schema` 初始化，再 `--profile all` 启动           |
| Volume 决定数据是否保留   | 删除 volume 会删除 PostgreSQL/ZooKeeper/资源/日志数据                           |
| `.env` 版本要匹配镜像   | `TAG` 默认是 `3.4.2`，本源码版本是 `3.4.3-SNAPSHOT`，本地构建时要注意一致 |
| 复用外部数据库时注意网络  | 容器内的 `localhost` 指容器自身，跨机器需要写真实 host 或使用 `--net host`  |

### 7. Kubernetes/Helm 注意事项

| 注意事项                     | 说明                                                             |
| ---------------------------- | ---------------------------------------------------------------- |
| 生产建议外置数据库           | 内置 PostgreSQL/MySQL 默认持久化关闭或演示配置，不应直接生产套用 |
| MinIO 是演示用途             | Helm 注释明确 MinIO 默认用于 demo，不推荐作为生产默认对象存储    |
| PVC 删除会删数据             | 卸载 Helm 不一定删除 PVC，手动删 PVC 会丢数据                    |
| MySQL 需要自定义镜像         | 所有服务和 Tools 都需要包含 MySQL Driver                         |
| ConfigMap 更新不一定自动重启 | `conf.auto=false` 时公共配置更新后需要手动重启组件             |
| API/Master/Worker 可扩缩容   | API 是 Deployment，Master/Worker 是 StatefulSet                  |
| Worker KEDA 是实验性         | 文档明确不建议生产依赖                                           |
| 探针路径要匹配 context path  | API 指标/健康路径带 `/gyyun`，其他服务通常是 `/actuator/...` |

## 八、典型部署链路

### 1. Standalone 快速体验链路

```text
解压二进制包
  -> daemon start standalone-server
  -> standalone start.sh 拼接 API/Master/Worker/Alert/插件 classpath
  -> Spring Boot 启动 StandaloneServer
  -> H2 schema 初始化
  -> JDBC Registry 可用
  -> API/Master/Worker/Alert 能力在同进程内运行
  -> 访问 /gyyun/ui
```

### 2. Docker Compose 快速体验链路

```text
docker-compose --profile schema up -d
  -> PostgreSQL healthy
  -> Tools 执行 upgrade-schema.sh
  -> 元数据库初始化完成

docker-compose --profile all up -d
  -> PostgreSQL + ZooKeeper
  -> API/Master/Worker/Alert 容器启动
  -> 各服务读取 .env 注入的数据库和 ZooKeeper 配置
  -> Master/Worker/Alert 注册心跳
  -> API 暴露 UI 和 REST
```

### 3. Helm/Kubernetes 快速部署链路

```text
helm upgrade --install
  -> 安装 subchart: PostgreSQL/ZooKeeper/MinIO(默认)
  -> 创建 ConfigMap/Secret/PVC/Service
  -> Helm hook Job 等待数据库 ready
  -> Tools Job 执行 upgrade-schema.sh
  -> API Deployment 启动
  -> Master StatefulSet 启动并选主
  -> Worker StatefulSet 启动并注册 WorkerGroup
  -> Alert Deployment 启动并进行 HA
  -> 通过 Ingress/NodePort/LoadBalancer/port-forward 访问 UI
```

## 九、部署排障入口

| 问题              | 优先检查                                                                |
| ----------------- | ----------------------------------------------------------------------- |
| UI 打不开         | API 进程/Pod、`12345` 端口、context path、Ingress/Service、API health |
| 登录失败          | 数据库初始化、默认用户是否存在、认证类型配置、API 日志                  |
| Master 不调度     | Master 是否 running、注册中心、Leader 状态、Quartz 表、数据库连接       |
| Worker 接不到任务 | Worker 是否注册、WorkerGroup 是否匹配、负载保护、Worker RPC 端口        |
| 任务执行失败      | Worker 日志、插件 jar、外部依赖路径、租户用户、sudo 权限、资源下载      |
| 定时任务不触发    | Schedule 状态、Master Leader、Quartz Scheduler、`QRTZ_` 表            |
| 告警不发送        | Alert 是否 Active、告警插件实例、告警组、SMTP/Webhook/API 凭证          |
| 数据源连接失败    | JDBC Driver、数据源插件、网络连通性、用户名密码、validation query       |
| 容器反复重启      | healthcheck/probe、数据库/注册中心连接、JVM 内存、配置环境变量          |
| Helm 安装卡住     | DB init Job、initContainer 等待数据库、subchart Pod、Secret/ConfigMap   |

## 十、最终总结

这个项目的快速部署机制可以概括为：

| 层次     | 核心机制                                                                                    |
| -------- | ------------------------------------------------------------------------------------------- |
| 构建层   | Maven Assembly 生成二进制包，`assembly-plugins.sh` 整理插件和共享依赖                     |
| 启动层   | 每个服务都有 `bin/start.sh`，顶层 `gyyun-daemon.sh` 负责 start/stop/status              |
| 初始化层 | `tools/bin/upgrade-schema.sh` 统一处理数据库初始化和升级                                  |
| 体验层   | Standalone 把 API/Master/Worker/Alert 放入一个进程，默认 H2 + JDBC Registry                 |
| 容器层   | Dockerfile 为每个服务生成独立镜像，Docker Compose 快速拉起 PostgreSQL、ZooKeeper 和核心服务 |
| 云原生层 | Helm Chart 用 Deployment/StatefulSet/Job/ConfigMap/Secret/PVC/Service 编排服务              |
| 云资源层 | Terraform/AWS 用 Packer + Terraform 自动创建 AMI、EC2、RDS、S3、ZooKeeper 等                |

从部署依赖上看，DolphinScheduler 的核心顺序是：先准备数据库和注册中心，再初始化 schema，然后启动 Master/Worker/Alert/API。API 面向用户，Master 负责调度，Worker 负责执行，Alert 负责告警，Tools 负责数据库生命周期，Standalone 负责快速体验。生产部署时最需要注意数据库持久化、注册中心高可用、插件依赖、MySQL 驱动、资源存储共享、sudo 权限、端口开放和 Kubernetes PVC/Secret/探针配置。
