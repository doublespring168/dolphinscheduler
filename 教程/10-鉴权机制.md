# 10-鉴权机制

本文档根据当前项目的 API、Service、DAO、SQL、前端路由/请求、认证子模块和部署配置整理，说明 DolphinScheduler 的用户、登录、鉴权机制是如何设计的，哪些功能性业务与鉴权耦合，以及如果要把剩余模块接到自己基于 Spring Boot + Spring Gateway 的微服务体系后面，应删除哪些模块、改造哪些功能。

## 一、结论总览

当前项目的鉴权不是 Spring Security 统一权限模型，而是一个以 `User` 为中心的自建机制：

| 层次 | 当前设计 | 关键源码/表 |
| --- | --- | --- |
| 登录认证 | API Server 通过 `Authenticator` 接口支持密码、LDAP、Casdoor SSO、OIDC，并额外支持 OAuth2 回调登录 | `gyyun-api/.../security/**`、`LoginController` |
| 会话认证 | 登录成功创建 `t_ds_session`，返回 `sessionId`；前端后续请求把 `sessionId` 放到请求头 | `SessionServiceImpl`、`t_ds_session`、`gyyun-ui/src/service/service.ts` |
| API Token | 请求头存在 `token` 时优先按 `t_ds_access_token` 查用户，绕过 session 方式 | `LoginHandlerInterceptor`、`AccessTokenServiceImpl`、`t_ds_access_token` |
| 当前用户注入 | `LoginHandlerInterceptor` 校验通过后把 `User` 写入 `request.setAttribute(Constants.SESSION_USER, user)` | `LoginHandlerInterceptor`、`Constants.SESSION_USER` |
| 业务授权 | Controller 从 `@RequestAttribute(Constants.SESSION_USER)` 取登录用户，Service 用 `loginUser` 做管理员判断、资源归属、操作权限、租户隔离 | `BaseServiceImpl`、`ResourcePermissionCheckServiceImpl` |
| 权限数据 | 项目、数据源、K8s namespace、资源/UDF 等通过用户-资源关系表控制授权 | `t_ds_relation_project_user`、`t_ds_relation_datasource_user`、`t_ds_relation_namespace_user` 等 |
| 用户业务语义 | `User` 不只是账号，还是项目/数据源/工作流/定时/命令/审计/资源租户的操作者和所有者 | `t_ds_user`、大量业务表中的 `user_id`、`operator`、`create_user_id` |

最重要的判断：

| 目标 | 建议 |
| --- | --- |
| 只去掉登录页和 DS 自己的 session | 可以做，改造量中等：让 Gateway 认证后把用户信息透传给 API，API 改成信任网关请求头 |
| 去掉 DS 的用户管理、密码、登录、token | 可以做，建议保留一个“内部用户上下文/影子用户表”作为兼容层 |
| 连 `t_ds_user`、`t_ds_tenant`、权限关系表都删除 | 不建议一步到位；这会牵动项目、工作流、资源中心、数据源、定时、审计、Python Gateway、Worker 多租户执行 |
| 完全让外部平台接管权限 | 可行，但需要重写资源授权服务和大量 `loginUser` 依赖点 |

## 二、用户模型

### 1. 用户表和用户实体

核心用户表是 `t_ds_user`，实体是 `gyyun-dao/src/main/java/org/apache/gyyun/dao/entity/User.java`。

| 字段/属性 | 作用 |
| --- | --- |
| `id` | 内部用户 ID，大量业务表使用它保存创建人、操作者、执行人 |
| `user_name` / `userName` | 登录名，也是 UI 展示、项目/数据源 owner 展示、Python Gateway 查询用户的依据 |
| `user_password` / `userPassword` | 密码认证使用，`UsersServiceImpl` 中用 MD5 保存和查询 |
| `user_type` / `userType` | 角色类型，`ADMIN_USER=0`、`GENERAL_USER=1` |
| `tenant_id` / `tenantId` | 绑定运行租户，资源中心目录和任务执行租户会用到 |
| `queue` | 用户自定义队列；为空时可退到租户对应队列 |
| `state` | 用户启停状态，`LoginHandlerInterceptor` 会拦截禁用用户 |
| `time_zone` | 登录用户时区，请求通过后写入 `ThreadLocalContext` |

`UserType` 只有两类：

| 类型 | 含义 |
| --- | --- |
| `ADMIN_USER` | 管理员，很多权限检查直接放行或可查看全部资源 |
| `GENERAL_USER` | 普通用户，只能访问自己创建或被授权的资源 |

### 2. 租户不是普通鉴权概念

`t_ds_tenant` 和 `Tenant` 实体看起来属于“安全中心/租户管理”，但它同时承担运行时语义：

| 租户用途 | 说明 |
| --- | --- |
| 资源目录隔离 | `ResourcesServiceImpl` 和资源校验器根据 `loginUser.tenantId` 找 `tenantCode`，拼接资源中心目录 |
| 工作流/定时执行 | `SchedulerServiceImpl` 保存 `tenantCode`，Worker 执行任务时会按租户语义运行 |
| 队列绑定 | 租户关联 `queue_id`，用户可继承租户队列 |
| Python API | `PythonGateway` 创建/查询租户并用用户租户编码创建定时 |

因此，想去掉登录鉴权时，不应直接删除 `t_ds_tenant`。更稳妥的做法是把外部平台的租户、部门、项目空间映射为 DS 的 `tenantCode`，或者至少保留一个默认租户。

## 三、登录认证机制

### 1. 认证类型选择

认证入口在 `gyyun-api/src/main/java/org/apache/gyyun/api/security/SecurityConfig.java`。

`security.authentication.type` 支持：

| 类型 | 实现类 | 作用 |
| --- | --- | --- |
| `PASSWORD` | `PasswordAuthenticator` | 用 `t_ds_user.user_name + user_password` 做本地账号密码登录 |
| `LDAP` | `LdapAuthenticator` + `LdapService` | 到 LDAP 校验账号密码，可按配置自动创建本地 DS 用户 |
| `CASDOOR_SSO` | `CasdoorAuthenticator` | 调 Casdoor 获取 OAuth token、解析用户并创建本地 DS 用户 |
| `OIDC` | `OidcAuthenticator` | 按 provider 做 OIDC 授权码流程，校验 ID Token、获取 UserInfo、映射用户组为管理员 |

此外还有一个独立的 OAuth2 回调登录：

| 入口 | 说明 |
| --- | --- |
| `/oauth2-provider` | 返回配置的 OAuth2 provider |
| `/redirect/login/oauth2` | 用授权码换 token，再取 userInfo，按用户名查询或创建本地用户，并创建 DS session |

这个 OAuth2 入口由 `OAuth2Configuration` 控制，和 `AuthenticationType` 枚举不是同一套分支。

### 2. 密码登录流程

密码登录的请求入口是 `LoginController.login`：

| 步骤 | 说明 |
| --- | --- |
| 1 | 前端调用 `POST /login`，提交 `userName`、`userPassword` |
| 2 | `LoginController` 检查用户名和客户端 IP |
| 3 | 调 `authenticator.authenticate(userName, userPassword, ip)` |
| 4 | `PasswordAuthenticator.login` 调 `userService.queryUser(userName, password)` |
| 5 | `UsersServiceImpl.queryUser(name, password)` 对明文密码做 MD5 后查 `t_ds_user` |
| 6 | 认证成功后 `AbstractAuthenticator` 调 `SessionService.createSessionIfAbsent(user)` |
| 7 | 返回 `sessionId` 和 `securityConfigType`，并写 HttpOnly Cookie |

本地密码机制依赖 `t_ds_user.user_password`。如果外部 Gateway 已经统一认证，建议不要继续暴露 DS 的密码登录和用户密码修改能力。

### 3. LDAP / SSO / OIDC 登录流程

| 方式 | 用户如何进入 DS | 用户如何落地 |
| --- | --- | --- |
| LDAP | 用户仍提交用户名密码，DS 到 LDAP 做 bind/search 校验 | 如果 `not-exist-action=CREATE`，自动创建 `t_ds_user` |
| Casdoor SSO | `/login/sso` 生成跳转地址，回调时校验 state 并解析 Casdoor 用户 | 不存在则创建 `t_ds_user`，管理员可按配置用户名映射 |
| OIDC | `/oauth2/authorization/{providerId}` 跳转，`/login/oauth2/code/{providerId}` 回调 | 校验 state、issuer、audience、过期时间；按 claim 取用户名，按 group 映射管理员，可自动创建用户 |
| OAuth2 | `/redirect/login/oauth2` 回调 | 取 userInfo 中的 `login` 字段，不存在则创建普通用户 |

这些外部认证方式并没有去掉 DS 用户体系，只是把“如何证明你是谁”交给外部系统；登录成功后仍然创建 `t_ds_session`，并仍然需要本地 `User` 对象参与业务权限。

## 四、请求鉴权链路

### 1. API 拦截器注册

`AppConfiguration.addInterceptors` 注册了三个拦截器：

| 拦截器 | 作用 |
| --- | --- |
| `LocaleChangeInterceptor` | 语言/国际化 |
| `RateLimitInterceptor` | 全局或 token 级限流 |
| `LoginHandlerInterceptor` | 登录校验和当前用户注入 |

`LoginHandlerInterceptor` 拦截 `/**/*`，排除：

| 排除路径 | 说明 |
| --- | --- |
| `/login/**` | 登录、SSO 登录、OIDC 回调等 |
| `/users/register` | 用户注册 |
| Swagger / OpenAPI / Knife4j 路径 | API 文档 |
| `*.html`、`/ui/**` | 前端静态资源 |
| `/oauth2-provider`、`/oidc-providers` | 登录页获取 provider |
| `/redirect/login/oauth2`、`/oauth2/authorization/**`、`/login/oauth2/code/**` | OAuth2/OIDC 回调 |
| `/cookies`、`/error` | 清 Cookie、错误页 |

### 2. 请求认证顺序

核心逻辑在 `LoginHandlerInterceptor.preHandle`：

| 顺序 | 逻辑 |
| --- | --- |
| 1 | API 请求计数加一 |
| 2 | 读取请求头 `token` |
| 3 | 如果 `token` 不为空，通过 `UserDao.queryUserByToken(token, new Date())` 查用户 |
| 4 | 如果 `token` 为空，调用 `authenticator.getAuthUser(request)` |
| 5 | `getAuthUser` 从请求头或 Cookie 取 `sessionId`，查 `t_ds_session` |
| 6 | 如果 session 超过 `Constants.SESSION_TIME_OUT=7200` 秒，删除该用户 session 并返回未登录 |
| 7 | 检查 `user.state`，禁用用户返回 401 |
| 8 | 把用户写入 `request.setAttribute(Constants.SESSION_USER, user)` |
| 9 | 把用户时区写入 `ThreadLocalContext` |

所以请求认证实际有两种凭据：

| 凭据 | 请求头 | 存储表 | 典型场景 |
| --- | --- | --- | --- |
| Session | `sessionId` | `t_ds_session` | UI 登录后的普通操作 |
| Access Token | `token` | `t_ds_access_token` | Open API、自动化调用、长期令牌 |

只要请求头里有 `token`，当前代码会优先走 token 查询，不再看 session。

### 3. Controller 当前用户注入

大量 Controller 方法形如：

```java
public Result<?> xxx(@RequestAttribute(value = Constants.SESSION_USER) User loginUser, ...)
```

源码中 `SESSION_USER` 在 API Controller 下有大量使用，项目、数据源、资源、工作流、定时、执行、监控、安全中心等接口都会拿到 `loginUser` 再传入 Service。当前代码不是在 Spring Security 的 `SecurityContext` 中取 Principal，而是依赖 `HttpServletRequest` attribute。

## 五、前端登录和鉴权机制

前端在 `gyyun-ui` 中维护登录状态。

| 前端位置 | 作用 |
| --- | --- |
| `src/views/login/**` | 登录页、SSO/OIDC/OAuth2 回调参数处理 |
| `src/service/modules/login/index.ts` | `/login`、`/login/sso`、`/oauth2-provider`、`/oidc-providers`、`/cookies` 请求 |
| `src/store/user/user.ts` | Pinia 持久化 `sessionId`、`securityConfigType`、`userInfo`、`baseResDir` |
| `src/service/service.ts` | Axios 请求拦截器把 `sessionId` 放入请求头；收到 401/504 清空用户状态并跳转 `/login` |
| `src/service/modules/logout/index.ts` | 调 `/signOut` 退出 |
| `src/router/index.ts` | 对安全中心管理页做管理员路由判断 |
| `src/router/modules/security.ts` | 安全中心菜单：租户、用户、告警组、Worker 组、队列、环境、集群、Token、K8s Namespace |

前端的管理员限制主要是 UI 层隐藏/跳转，真正的安全控制仍在后端 Service 中。

如果接入自建 Spring Gateway，前端通常应改成：

| 原逻辑 | 改造方向 |
| --- | --- |
| 访问 DS 登录页 | 改为访问统一登录页，或 Gateway 未登录时重定向统一认证 |
| 保存 `sessionId` | 保存外部平台 token，或完全由 Gateway Cookie 管理 |
| 每个请求发 `sessionId` | 改发外部 `Authorization`，或不显式发凭据，由 Gateway 注入内部头 |
| 401 后跳 `/login` | 改跳统一登录地址 |
| DS 安全中心用户/Token 页面 | 删除、隐藏或改为只读展示外部用户信息 |

## 六、业务授权机制

### 1. 基础权限工具

`BaseServiceImpl` 是很多 Service 的父类，里面有几类核心权限判断：

| 方法 | 作用 |
| --- | --- |
| `isAdmin(User user)` | 判断 `user.userType == ADMIN_USER` |
| `isNotAdmin(User loginUser)` | 管理员专用接口常用 |
| `canOperator(User operateUser, int createUserId)` | 创建人本人或管理员可操作 |
| `canOperatorPermissions(User user, Object[] ids, AuthorizationType type, String permissionKey)` | 同时检查操作权限和资源权限 |

`canOperatorPermissions` 会做两件事：

| 检查 | 说明 |
| --- | --- |
| 操作权限 | `resourcePermissionCheckService.operationPermissionCheck(type, userId, permissionKey, log)` |
| 资源权限 | `resourcePermissionCheckService.resourcePermissionCheck(type, ids, admin ? 0 : userId, log)` |

`ResourcePermissionCheckServiceImpl` 按 `AuthorizationType` 分派资源授权查询。

### 2. 资源授权类型

当前资源授权包括：

| `AuthorizationType` | 授权/过滤方式 |
| --- | --- |
| `PROJECTS` | 查项目创建人和 `t_ds_relation_project_user` |
| `DATASOURCE` | 查数据源创建人和 `t_ds_relation_datasource_user` |
| `K8S_NAMESPACE` | 查 `t_ds_relation_namespace_user` |
| `TASK_GROUP` | 查询用户可见任务组 |
| `ENVIRONMENT` | 管理员可配置，列表查询按授权资源集过滤 |
| `WORKER_GROUP` | 管理员可配置，列表查询按授权资源集过滤 |
| `ALERT_GROUP` | 按告警组资源集过滤 |
| `TENANT` | 租户管理权限 |
| `QUEUE` | 队列管理权限 |
| `ACCESS_TOKEN` | Token 管理权限 |
| `ALERT_PLUGIN_INSTANCE` | 告警实例相关权限 |

不是所有资源都有完整的“按钮级权限”实现，有些 `permissionCheck` 直接返回 `true` 或 `false`，实际效果依赖管理员判断、资源列表查询和业务 Service 的额外限制。

### 3. 项目权限

项目是业务授权最核心的资源。

| 场景 | 权限逻辑 |
| --- | --- |
| 创建项目 | `ProjectServiceImpl.createProject` 调 `canOperatorPermissions(PROJECTS, PROJECT_CREATE)` |
| 查看项目 | `checkProjectAndAuthThrowException` 检查项目存在和项目授权 |
| 修改/删除项目 | 要有项目写权限，管理员或项目 owner 或 `ProjectUser.perm=7` |
| 查询项目列表 | 管理员查全部，普通用户查创建/授权项目 |
| 授权用户 | `UsersServiceImpl.grantProject*` 写 `t_ds_relation_project_user` |

这意味着工作流、任务定义、定时、执行、实例查询等所有“挂在项目下”的功能，都会间接依赖项目授权。

### 4. 数据源权限

数据源权限在 `DataSourceServiceImpl` 中体现明显：

| 场景 | 权限逻辑 |
| --- | --- |
| 创建数据源 | 需要 `DATASOURCE_CREATE_DATASOURCE` |
| 查询/编辑/删除数据源 | 需要对应数据源 ID 的资源权限 |
| 查询库表/字段 | 也检查数据源资源权限 |
| 授权用户 | `UsersServiceImpl.grantDataSource` 写 `t_ds_relation_datasource_user` |
| 列表 | 管理员看全部，普通用户只看授权数据源 |

如果外部平台接管数据源权限，需要重写这些检查，否则删除用户关系表后普通用户会无法看到数据源。

### 5. 资源中心和租户耦合

资源中心不是简单的“文件管理”，它把用户、租户和存储路径绑定起来：

| 源码 | 耦合点 |
| --- | --- |
| `ResourcesServiceImpl.queryResourceFiles` | 根据 `loginUser.tenantId` 查租户，再取租户资源目录 |
| `ResourcesServiceImpl.queryResourceBaseDir` | 查当前用户和租户，返回当前用户可用资源根目录 |
| `PagingResourceItemRequestTransformer` | 管理员查所有租户目录，普通用户只查自己租户目录 |
| `AbstractResourceValidator.exceptionUserNoResourcePermission` | 从资源路径解析 tenant，与用户 tenant 比较，不一致则拒绝 |

因此，如果去掉用户体系但保留资源中心，必须提供一个可用的 `tenantId/tenantCode` 映射，否则资源上传、下载、查看、重命名都会出错或越权。

### 6. 工作流、定时和执行耦合

工作流相关模块大多通过项目授权间接鉴权，同时把 `loginUser` 写入业务数据：

| 模块 | 耦合点 |
| --- | --- |
| `WorkflowDefinitionServiceImpl` | 创建/更新/删除/上线/下线/复制/移动/版本切换都检查项目权限；创建或复制时写 `userId=loginUser.id` |
| `SchedulerServiceImpl` | 创建/更新/上线/下线定时先检查项目权限；保存 `userId`、`userName`、`tenantCode` |
| `ExecutorServiceImpl` | 触发、控制、恢复、暂停、停止工作流时检查项目权限；创建命令时写 `executorId=loginUser.id` |
| `WorkflowInstanceServiceImpl`、`TaskInstanceServiceImpl` | 查询、控制、变量、甘特图等按项目权限或实例归属限制 |
| `ProcessService` 相关保存逻辑 | 保存任务定义、工作流定义、日志版本时传入 `loginUser` 作为 operator/creator |

这些字段不是登录层字段，而是审计、归属、展示、调度执行都会用到的业务字段。

### 7. 管理类资源耦合

安全中心中的很多页面看起来是“鉴权管理”，但其中一部分也是业务配置：

| 功能 | 是否能直接删除 | 原因 |
| --- | --- | --- |
| 用户管理 | 可删除 UI/API，但需保留用户兼容层或重写业务 owner 字段 | 大量 Service 需要 `User` |
| Token 管理 | 如果外部 Gateway 统一颁发 token，可删除 | 当前只服务 DS 自有 API token |
| 租户管理 | 不建议直接删除 | Worker 多租户执行、资源目录和定时执行依赖 tenant |
| Yarn 队列管理 | 不建议简单删除 | 租户和用户队列会引用 |
| Worker 分组管理 | 不属于登录鉴权，可保留 | 工作流执行选择 WorkerGroup 需要 |
| 环境管理 | 不属于登录鉴权，可保留但要重写管理员限制 | 任务运行环境依赖 |
| 集群管理 | 不属于登录鉴权，可保留但要重写管理员限制 | K8s 等运行配置依赖 |
| 告警组/告警实例 | 不属于登录鉴权，可保留但要改操作者/创建人 | 工作流告警依赖 |
| K8s Namespace 管理 | 不属于登录鉴权，可保留但要重写用户授权关系 | K8s 任务运行依赖 |

## 七、功能性业务中的鉴权耦合点

当前项目中，用户/鉴权与功能业务有明显耦合，不是删掉 `LoginController` 就结束。

| 耦合点 | 典型位置 | 改造影响 |
| --- | --- | --- |
| Controller 方法参数 | 大量 `@RequestAttribute(Constants.SESSION_USER) User loginUser` | 去掉拦截器后 Controller 会拿不到参数 |
| 管理员判断 | `isAdmin`、`isNotAdmin` | 需要把外部角色映射为 DS 内部角色或新权限判断 |
| 资源归属过滤 | `ResourcePermissionCheckServiceImpl` | 外部平台接管权限时要重写 |
| 项目授权 | `t_ds_relation_project_user`、`ProjectServiceImpl` | 工作流相关几乎都受影响 |
| 数据源授权 | `t_ds_relation_datasource_user`、`DataSourceServiceImpl` | 数据源列表、连接测试、库表字段查询受影响 |
| 资源中心租户隔离 | `ResourcesServiceImpl`、资源 validators | 必须保留或替换 tenant 语义 |
| K8s Namespace 授权 | `t_ds_relation_namespace_user`、`K8sNamespaceServiceImpl` | K8s 任务可用 namespace 列表受影响 |
| 创建人/操作者字段 | `user_id`、`operator`、`create_user_id` | 影响展示、审计、删除限制、版本日志 |
| 定时/执行人字段 | `Schedule.userId`、`Command.executorId` | 影响定时归属和执行追踪 |
| 审计日志 | `OperatorLogAspect`、`AuditLog.userId` | 审计必须能拿到用户 ID |
| API Token | `t_ds_access_token`、`AccessTokenServiceImpl` | 外部 Gateway 统一鉴权时应删除或停用 |
| 限流 | `RateLimitInterceptor` 使用请求头 `token` 做 tenant-level 限流 | 若 token 由 Gateway 管理，建议迁移限流到 Gateway |
| Python Gateway | `PythonGateway` 通过 `userName` 查 `User`，创建项目授权关系 | Python API 调用必须有外部用户到内部用户的映射 |
| 删除用户限制 | `UsersServiceImpl.deleteUserById` 检查项目 owner、删除 token/session | 外部用户管理后需要改成禁用/解绑或不提供删除 |

源码粗略统计中，API Controller 内对 `SESSION_USER` 的使用很多，Service 层 `User loginUser` 和 `canOperatorPermissions/checkProjectAndAuth/isAdmin` 也大量存在。这说明用户对象已经是服务层方法签名的一部分。

## 八、放到自建 Spring Boot + Spring Gateway 后的推荐架构

### 1. 推荐总体方案

不要让 DS 再负责“认证”，但保留一个“用户上下文适配层”：

| 层 | 职责 |
| --- | --- |
| Spring Gateway | 统一认证登录、校验外部 JWT/Cookie/Session、做全局鉴权和限流 |
| Gateway 到 DS 的内部请求 | 透传可信请求头，如 `X-User-Id`、`X-Username`、`X-User-Role`、`X-Tenant-Code`、`X-Request-Id` |
| DS API | 不再校验 DS session/token，而是从可信请求头构造或查询内部 `User` |
| DS Service | 短期继续接收 `User loginUser`，避免大面积改方法签名 |
| DS DAO | 短期保留 `t_ds_user`、`t_ds_tenant` 和业务 `user_id` 字段 |
| 外部权限中心 | 决定用户能否访问某项目/数据源/命名空间；DS 通过适配器查询或同步权限 |

推荐的请求链路：

```text
浏览器/调用方
  -> Spring Gateway 认证外部 token/cookie
  -> Gateway 校验路由权限并注入内部请求头
  -> DS API HeaderUserInterceptor 构造 User
  -> request.setAttribute(Constants.SESSION_USER, user)
  -> 原 Controller / Service 基本保持
```

### 2. 当前 DS 拦截器如何替换

新增或替换一个网关头解析拦截器，例如 `GatewayUserContextInterceptor`：

| 原 `LoginHandlerInterceptor` | 新拦截器 |
| --- | --- |
| 读 `token` 或 `sessionId` | 读 Gateway 注入的 `X-User-*` |
| 查 `t_ds_access_token` 或 `t_ds_session` | 查/同步 `t_ds_user`，或构造虚拟 `User` |
| 检查 `user.state` | 可保留为内部禁用开关，也可改由 Gateway 控制 |
| 写 `Constants.SESSION_USER` | 继续写，兼容所有 Controller |
| 写用户时区 | 从用户表或请求头中取时区 |

短期最小改造可以这样做：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 固定系统管理员用户 | 改动最小，所有业务放开 | 没有业务级隔离，审计全是同一个用户 |
| 外部用户自动同步为内部 `t_ds_user` | 保留审计和 owner 语义，改动可控 | 仍保留内部用户表 |
| 完全虚拟 User，不落库 | 去账号化彻底 | 很多 DAO 会按 userId 查关系或展示用户名，改造面大 |

建议采用第二种：外部用户首次进入时自动创建/同步一条内部用户记录，密码为空或不可登录，`userName` 存外部用户名，`userType` 由外部角色映射，`tenantId` 由外部租户映射。

## 九、可以删除或禁用的模块

### 1. 后端可删除/禁用的登录认证模块

如果 Gateway 完全负责认证，以下 API 登录能力可以删除或禁用：

| 类/目录 | 处理建议 | 原因 |
| --- | --- | --- |
| `gyyun-api/.../security/AuthenticationType.java` | 删除或废弃 | DS 不再选择认证类型 |
| `gyyun-api/.../security/Authenticator.java` | 删除或替换为 Gateway 用户解析接口 | 不再做用户名密码/session 认证 |
| `gyyun-api/.../security/SecurityConfig.java` | 删除或改为注册新 Header 拦截器所需 Bean | 不再按 `security.authentication.type` 创建 Authenticator |
| `gyyun-api/.../security/impl/AbstractAuthenticator.java` | 删除 | session 登录逻辑无用 |
| `impl/pwd/PasswordAuthenticator.java` | 删除 | 本地密码登录无用 |
| `impl/ldap/**` | 删除 | LDAP 登录交给 Gateway 或统一身份中心 |
| `impl/sso/CasdoorAuthenticator.java` | 删除 | Casdoor 登录交给 Gateway |
| `impl/oidc/**` | 删除 | OIDC 登录交给 Gateway |
| `LoginController` 中 `/login`、`/login/sso`、OAuth2/OIDC 回调、`/signOut`、`/cookies` | 删除或只保留兼容跳转 | 登录退出由统一认证体系负责 |
| `OAuth2Configuration` | 删除 | OAuth2 provider 不再由 DS 暴露 |
| `SessionService`、`SessionServiceImpl` | 删除 | 不再使用 `t_ds_session` |
| `SessionDao`、`SessionMapper`、`Session` 实体 | 删除 | 同上 |

注意：如果仍想允许老客户端用 DS token 调 API，则不能删除 `AccessToken`。如果 Gateway 也接管机器调用，才建议删除。

### 2. 后端可删除/禁用的 Access Token 模块

| 类/表/前端 | 处理建议 |
| --- | --- |
| `AccessTokenController` | 删除或下线路由 `/access-tokens` |
| `AccessTokenService`、`AccessTokenServiceImpl` | 删除 |
| `AccessTokenDao`、`AccessTokenMapper`、`AccessToken` 实体 | 删除 |
| `t_ds_access_token` | 可删除 |
| `UserDao.queryUserByToken`、`UserMapper.queryUserByToken` | 删除 |
| `LoginHandlerInterceptor` 中读取 header `token` 的逻辑 | 删除 |
| 前端 `src/service/modules/token/**`、`views/security/token-manage/**` | 删除或隐藏 |

若保留外部“服务账号/机器人调用”，建议由 Gateway 验证外部 token，再注入普通用户头或服务账号头给 DS，不再让 DS 存长期 token。

### 3. 前端可删除/改造的登录模块

| 前端文件/目录 | 处理建议 |
| --- | --- |
| `src/views/login/**` | 删除，或改为跳转统一登录页 |
| `src/service/modules/login/**` | 删除 |
| `src/service/modules/logout/**` | 改为调用统一退出地址 |
| `src/store/user/user.ts` 中 `sessionId/securityConfigType` | 删除或替换为外部登录态字段 |
| `src/store/user/types.ts` | 同步修改 |
| `src/service/service.ts` | 删除 `sessionId` 请求头，改为外部 `Authorization` 或不发，由 Gateway Cookie 认证 |
| `src/router/routes.ts` 的 `/login` 路由 | 删除或改为外部跳转页 |
| 401/504 处理 | 改跳统一登录页，而不是 `/login` |
| `src/router/index.ts` 管理员判断 | 改用外部角色/权限，或由后端返回菜单权限 |

### 4. 认证子模块的处理

`gyyun-authentication` 目录需要区分看：

| 子模块 | 是否是 DS 登录鉴权 | 建议 |
| --- | --- | --- |
| `gyyun-actuator-authentication` | 不是业务登录，是 Actuator HTTP Basic | 如果 Gateway/运维网关已经保护 `/actuator/**`，可以移除依赖或保持 `management.security.enabled=false` |
| `gyyun-aws-authentication` | 不是用户登录，是 AWS 凭证 Provider | 不要因为“去鉴权”误删；S3、EMR、SageMaker、DMS、DataSync 等插件可能依赖它 |

`gyyun-actuator-authentication` 被 API/Master/Worker/Alert 引用；`gyyun-aws-authentication` 被 Common、S3 存储插件和多个 AWS 任务插件引用。

## 十、需要改造但不建议直接删除的模块

### 1. UsersService 和 UserDao

如果外部平台管理用户，`UsersController` 可以删除或下线，但 `UsersService` / `UserDao` 不建议立即删除。

建议改造成“内部用户映射服务”：

| 原能力 | 改造后 |
| --- | --- |
| 创建用户、修改密码、启停用户 | 从外部用户中心同步或首次访问自动创建 |
| 查询当前用户信息 | 返回外部用户映射后的内部用户信息 |
| 管理员判断 | 由外部角色映射 `ADMIN_USER/GENERAL_USER` |
| 删除用户 | 改为禁用内部映射或解绑外部 ID，避免破坏项目 owner |
| 密码字段 | 置空、随机不可用值或废弃 |

需要新增字段时，可考虑在 `t_ds_user` 增加：

| 字段 | 用途 |
| --- | --- |
| `external_user_id` | 外部统一用户 ID |
| `external_tenant_id` | 外部租户/组织 ID |
| `source` | 用户来源，如 `gateway`、`iam` |

### 2. TenantService

`TenantController` 可从“安全中心”移出或改为平台内部配置，但 `TenantService` 及 `t_ds_tenant` 建议保留。

改造方向：

| 原能力 | 改造后 |
| --- | --- |
| 管理员在 DS UI 创建租户 | 外部平台创建租户/空间时同步 DS tenant |
| 用户绑定 `tenantId` | Gateway 头中带 `X-Tenant-Code`，DS 查找/创建 tenant 后绑定当前内部用户 |
| 资源中心按用户 tenant 隔离 | 继续保留，或改为项目空间隔离 |
| 定时执行选择 tenantCode | 由外部平台策略决定默认 tenantCode |

### 3. ProjectService 和项目授权

如果外部平台接管项目权限，有两种路线：

| 路线 | 改法 |
| --- | --- |
| 兼容路线 | 继续维护 `t_ds_relation_project_user`，外部授权变化时同步到 DS |
| 重写路线 | 改 `ProjectServiceImpl.checkProjectAndAuthThrowException` 和 `ResourcePermissionCheckServiceImpl.ProjectsResourcePermissionCheck`，实时调用外部权限服务 |

如果只是把所有 DS API 放在 Gateway 后面且内部可信，也可以临时把外部平台授权后的请求映射为管理员，但这会失去 DS 内部项目隔离。

### 4. DataSourceService 和数据源授权

改造方式类似项目：

| 路线 | 改法 |
| --- | --- |
| 兼容路线 | 外部平台授权数据源时同步 `t_ds_relation_datasource_user` |
| 重写路线 | 数据源列表、详情、连接测试、库表字段查询都调用外部权限服务 |
| 完全开放 | 只适合 DS 后端已被 Gateway 按数据源权限精确拦截的情况 |

### 5. 资源中心授权

资源中心必须决定“某用户能看哪个目录”。

推荐改造：

| 原逻辑 | 改造后 |
| --- | --- |
| 管理员看所有租户目录 | 外部管理员角色看全部 |
| 普通用户看自己 tenant 目录 | 外部租户/项目空间映射为 DS tenant 或资源空间 |
| 校验路径 tenant 与用户 tenant 一致 | 改为路径 space 与 Gateway claims 一致 |

如果你的平台已经有统一文件中心，也可以删除 DS 资源中心 UI/API，但工作流任务引用资源文件的能力需要另行适配。

### 6. 审计日志

`OperatorLogAspect` 通过方法参数里的 `User` 构造 `AuditLog.userId`。如果删除用户对象，审计会拿不到操作者。

建议：

| 方案 | 说明 |
| --- | --- |
| 保留内部 userId | 最小改造，审计仍写 `user_id` |
| 增加外部用户字段 | `t_ds_audit_log` 增加 `external_user_id`、`external_user_name` |
| 改审计上下文 | 从 Gateway 请求头或统一 `CurrentUserContext` 取操作者 |

### 7. Python Gateway

`PythonGateway` 多处通过 `userName` 查 `User`，再调用项目、工作流、定时和执行服务；还会在项目不是该用户创建时自动写 `ProjectUser` 授权关系。

如果仍使用 Python API，需要：

| 当前行为 | 改造 |
| --- | --- |
| Python 传 `userName` | 改传外部 token，或传外部用户 ID 后映射内部用户 |
| `usersService.queryUser(userName)` | 改为 `ExternalUserMappingService.getOrCreateUser(...)` |
| 自动写 `ProjectUser` | 改为同步外部授权，或保留兼容关系表 |

## 十一、数据库表处理建议

### 1. 可以优先删除的表

在完全由 Gateway 管理登录态和机器 token 后，可以删除：

| 表 | 删除条件 |
| --- | --- |
| `t_ds_session` | 不再使用 DS `sessionId` |
| `t_ds_access_token` | 不再使用 DS header `token` |

对应 SQL 初始化、升级脚本、Mapper、DAO、实体也要同步删除，否则构建或运行会出现引用错误。

### 2. 暂时保留的表

以下表虽然看起来属于用户/安全，但短期应保留：

| 表 | 保留原因 |
| --- | --- |
| `t_ds_user` | 项目、工作流、任务、定时、命令、审计、Python API 都依赖内部 userId |
| `t_ds_tenant` | 资源目录、队列、Worker 多租户执行、定时 tenantCode 依赖 |
| `t_ds_project` 中 `user_id/user_name` | 项目 owner 和展示依赖 |
| `t_ds_workflow_definition`、`t_ds_task_definition`、日志表中的 `user_id/operator` | 版本、创建人、操作人依赖 |
| `t_ds_schedules.user_id` | 定时归属依赖 |
| `t_ds_command.executor_id` | 执行人追踪依赖 |
| `t_ds_audit_log.user_id` | 审计依赖 |
| `t_ds_alertgroup.create_user_id` | 告警组创建人依赖 |
| `t_ds_environment.operator`、`t_ds_cluster.operator` 等 | 管理操作人依赖 |

### 3. 可在权限外置后删除的关系表

只有在所有资源授权都改为外部权限服务或 Gateway 精确拦截后，才考虑删除：

| 表 | 替代逻辑 |
| --- | --- |
| `t_ds_relation_project_user` | 外部项目权限服务 |
| `t_ds_relation_datasource_user` | 外部数据源权限服务 |
| `t_ds_relation_namespace_user` | 外部 K8s Namespace 权限服务 |
| `t_ds_relation_resources_user` | 外部资源中心权限服务；当前代码引用较少，但历史 SQL 存在 |
| `t_ds_relation_udfs_user` | 外部 UDF 权限服务；当前代码引用较少，但历史 SQL 存在 |

## 十三、推荐迁移步骤

### 阶段 1：先放到 Gateway 后面，不动 DS 内部鉴权

| 目标 | 做法 |
| --- | --- |
| 降低风险 | Gateway 先只做入口认证、TLS、路由、基础限流 |
| 保持兼容 | DS 登录、session、token 仍可用 |
| 观察接口 | 梳理外部平台真正需要暴露哪些 DS API |

### 阶段 2：新增 Gateway 用户上下文适配

| 目标 | 做法 |
| --- | --- |
| 取消 DS 登录依赖 | 新增 Header 拦截器，读取 `X-User-*` |
| 兼容现有 Service | 继续写 `Constants.SESSION_USER` |
| 保留业务语义 | 自动同步/创建内部 `t_ds_user` |
| 保留租户运行能力 | 外部租户映射为 DS `tenantCode` |

### 阶段 3：替换前端登录态

| 目标 | 做法 |
| --- | --- |
| 删除 DS 登录页 | `/login` 改为统一登录跳转 |
| 删除 `sessionId` | Axios 不再发 DS session |
| 保留用户信息展示 | `/users/get-user-info` 改为返回 Gateway 映射用户 |
| 菜单权限外置 | 前端管理员菜单按外部角色展示 |

### 阶段 4：下线 DS Session 和 Access Token

| 目标 | 做法 |
| --- | --- |
| 删除 session | 删除 `SessionService`、`t_ds_session`、session 查询逻辑 |
| 删除 token | 删除 `/access-tokens`、`t_ds_access_token`、header `token` 认证 |
| 限流迁移 | `RateLimitInterceptor` 的 token 级限流迁到 Gateway |

### 阶段 5：资源授权外置

| 目标 | 做法 |
| --- | --- |
| 项目权限外置 | 重写 `ProjectServiceImpl` 权限检查或同步关系表 |
| 数据源权限外置 | 重写 `DataSourceServiceImpl` 权限过滤或同步关系表 |
| 资源中心权限外置 | 重写租户目录校验 |
| K8s Namespace 权限外置 | 替换 `t_ds_relation_namespace_user` |

### 阶段 6：再决定是否删除内部用户表

只有当以下条件都满足，才考虑删除 `t_ds_user`：

| 条件 | 说明 |
| --- | --- |
| 所有业务表的 `user_id/operator/create_user_id` 已改为外部 ID 或字符串 |
| 所有 Service 方法不再依赖 `User loginUser` |
| 审计已支持外部用户 |
| 项目、数据源、资源、K8s Namespace 权限完全外置 |
| Python Gateway、定时执行、Worker 多租户执行已完成适配 |

在多数集成场景中，更现实的方案是长期保留内部 `t_ds_user` 作为“外部用户到 DS 业务归属”的映射表。

## 十四、注意事项

| 注意事项 | 说明 |
| --- | --- |
| 不要把 `gyyun-authentication` 全部当成登录模块 | AWS 子模块是云资源凭证，不是用户登录 |
| 不要直接删除 `t_ds_tenant` | 它参与资源目录、队列和任务执行 |
| 不要只删前端登录页 | 后端拦截器仍会要求 `sessionId/token` |
| 不要让外部请求直接访问 DS API | 如果采用可信请求头，必须保证只有 Gateway 能访问 DS 后端 |
| 不要让用户伪造 `X-User-*` | DS API 应校验来源 IP、内网、mTLS 或 Gateway 签名头 |
| 不要把所有人都映射成管理员后长期运行 | 会破坏项目/数据源/资源隔离，审计也会失真 |
| 不要忽略机器调用 | 原 `token` 能支持自动化调用，迁移后要在 Gateway 提供 service account 机制 |
| 不要忽略审计 | 删除用户后，`OperatorLogAspect` 需要新的操作者来源 |
| 不要忽略 Python API | `PythonGateway` 直接按 `userName` 查本地用户 |
| 不要忽略资源中心 | 资源路径中含 tenant 语义，和登录用户租户强相关 |

## 十五、最终改造清单

### 1. 建议删除/下线

| 类别 | 清单 |
| --- | --- |
| API 登录认证 | `LoginController` 登录/退出/OAuth/OIDC 相关接口，`security/**` 下的 Password/LDAP/Casdoor/OIDC 实现 |
| Session | `SessionService*`、`SessionDao/Mapper/Entity`、`t_ds_session` |
| DS Access Token | `AccessTokenController`、`AccessTokenService*`、`AccessTokenDao/Mapper/Entity`、`t_ds_access_token` |
| 前端登录 | `views/login/**`、`service/modules/login/**`、`service/modules/logout/**` |
| 前端 token 管理 | `views/security/token-manage/**`、`service/modules/token/**` |
| 认证配置 | `security.authentication.*`、`casdoor.*`、OAuth2/OIDC provider 配置 |

### 2. 建议改造

| 类别 | 清单 |
| --- | --- |
| API 拦截器 | 用 Gateway Header 拦截器替代 `LoginHandlerInterceptor`，继续写 `Constants.SESSION_USER` |
| 用户服务 | `UsersService` 改为外部用户映射/同步服务 |
| 前端请求 | `service.ts` 删除 `sessionId`，改走 Gateway 登录态 |
| 当前用户接口 | `/users/get-user-info` 返回外部用户映射信息 |
| 项目权限 | `ProjectServiceImpl`、`ResourcePermissionCheckServiceImpl.ProjectsResourcePermissionCheck` |
| 数据源权限 | `DataSourceServiceImpl`、`DataSourceResourcePermissionCheck` |
| 资源中心 | `ResourcesServiceImpl` 和 `api/validator/resource/**` 的 tenant 校验 |
| 租户 | `TenantServiceImpl` 改为外部租户同步或默认租户策略 |
| 定时/执行 | `SchedulerServiceImpl`、`ExecutorServiceImpl` 中 userId、tenantCode、executorId 来源 |
| 审计 | `OperatorLogAspect`、`AuditLog` 操作者来源 |
| 限流 | `RateLimitInterceptor` token 级限流迁到 Gateway |
| Python API | `PythonGateway` 的 userName -> User 查询和项目授权 |

### 3. 建议保留

| 类别 | 清单 |
| --- | --- |
| 内部业务用户映射 | `t_ds_user`、`User`、`UserDao`，至少短期保留 |
| 运行租户 | `t_ds_tenant`、`TenantService`，至少短期保留 |
| Worker/环境/集群/队列/告警业务配置 | 这些不是登录机制本身，只需替换管理员权限判断 |
| AWS 认证子模块 | 使用 S3/EMR/SageMaker/DMS/DataSync 等能力时保留 |
| Actuator 认证子模块 | 可由 Gateway 替代；如保留则只保护运维端点 |

## 十六、建议落地形态

最推荐的落地形态是：

1. Spring Gateway 负责统一登录、JWT/Cookie 校验、服务账号校验、粗粒度路由权限、限流。
2. DS API 只信任来自 Gateway 的内部请求头，不再暴露 DS 登录、session、access token。
3. DS 内部保留 `t_ds_user` 作为外部用户映射表，保留 `t_ds_tenant` 作为运行租户表。
4. 短期同步外部项目/数据源权限到 DS 关系表，减少改造面。
5. 中长期再把 `ResourcePermissionCheckServiceImpl` 替换为外部权限服务查询。

这样可以达到“去掉本项目用户、登录、鉴权机制”的主要目标：用户身份和访问控制由你的 Spring Boot + Spring Gateway 微服务体系统一负责；同时避免一次性破坏 DolphinScheduler 中已经深度依赖 `User`、`Tenant`、`user_id`、`operator` 的调度业务模型。
