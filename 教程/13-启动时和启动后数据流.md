# 启动时和启动后数据流

本文分析整个项目中各模块在启动时执行的动作，以及启动后持续执行或被请求触发的动作。这里的“模块”分两类：

- 可独立启动的进程模块：`gyyun-api`、`gyyun-master`、`gyyun-worker`、`gyyun-alert-server`、`gyyun-standalone-server`、`gyyun-tools`。
- 被进程模块引入的基础库和插件模块：`gyyun-common`、`gyyun-dao`、`gyyun-service`、`gyyun-registry`、`gyyun-scheduler-plugin`、`gyyun-task-executor`、各类 plugin、`gyyun-extract` 等。

一句话概括：

```text
启动时：Spring Boot 装配基础设施 -> 注册 RPC / 注册中心 / 插件 / 调度器 / 后台线程
启动后：API 接收 HTTP -> Master 消费 command 并推进 DAG -> Worker 执行任务 -> Alert 发送告警
```

## 1. 总体启动地图

项目的生产部署通常由四个常驻服务组成：

| 服务 | 主类 | 启动时核心动作 | 启动后核心动作 |
| --- | --- | --- | --- |
| API | `com.gyyun.ds.api.ApiApplicationServer` | 启动 Jetty/Spring MVC，装配 DAO、Service、Storage、Registry，加载任务/数据源插件 | 接收 UI/SDK/外部 HTTP 请求，做鉴权、权限、参数校验，然后访问 DB、Storage、Registry 或 RPC 调 Master/Worker/Alert |
| Master | `com.gyyun.ds.server.master.MasterServer` | 启动 Master RPC、插件、注册中心心跳、HA coordinator、集群订阅、工作流引擎、Quartz、系统事件线程 | 轮询 `t_ds_command`，创建工作流执行上下文，推进 DAG 状态机，分发任务，处理 Worker 回调和 failover |
| Worker | `com.gyyun.ds.server.worker.WorkerServer` | 启动 Worker RPC，加载任务/数据源插件，注册 Worker 心跳，启动物理任务引擎和生命周期上报器 | 接收 Master 下发的 `TaskExecutionContext`，创建任务执行器，执行具体任务插件，上报生命周期事件 |
| Alert | `com.gyyun.ds.alert.AlertServer` | 加载告警插件，启动 Alert RPC，写 Alert 心跳，参与 Alert HA 选主 | active 节点轮询 `t_ds_alert`，调用告警插件发送，回写告警状态；也响应同步/测试告警 RPC |
| Standalone | `com.gyyun.ds.StandaloneServer` | 单 JVM 扫描并装配 API/Master/Worker/Alert 相关 Bean，默认 H2 + JDBC Registry | 在一个进程内同时具备 API、Master、Worker、Alert 的启动后行为 |

有些模块没有自己的常驻进程，例如 `gyyun-common`、`gyyun-dao`、`gyyun-spi`、`gyyun-extract`。它们的启动动作体现为被上面服务导入后创建 Bean、启动自动配置、提供 SPI/RPC/DAO 能力。

## 2. Spring Boot 公共启动阶段

所有 Java 服务大致都会经历：

```text
main()
  -> 设置线程名 / 异常处理 / 指标
  -> SpringApplication.run(...)
  -> 读取 application.yaml 与 profile
  -> 自动配置 DataSource、MyBatis、Quartz、Registry、Metrics、Actuator
  -> 扫描 @Component / @Service / @Controller
  -> 执行 BeanPostProcessor、@PostConstruct、CommandLineRunner、ApplicationReadyEvent
  -> 服务进入 RUNNING
```

公共基础动作如下：

| 模块 | 启动时动作 | 作用 |
| --- | --- | --- |
| `gyyun-common` | `CommonConfiguration` 扫描 `com.gyyun.ds.common`；`RemoteLogUtils.@PostConstruct` 保存 `RemoteLogService` 静态引用 | 提供生命周期、线程、日志、时间、JSON、远程日志等公共能力 |
| `gyyun-dao` | `DaoConfiguration` 扫描 DAO/Mapper，创建 MyBatis-Plus 分页拦截器、`DatabaseIdProvider`、`DbType`、`DatabaseMonitor`、`DatabaseDialect` | 让上层服务可以访问元数据库，并根据 MySQL/PostgreSQL/H2 选择正确方言 |
| `gyyun-dao-plugin` | 通过 `spring.factories` 条件加载 MySQL/PostgreSQL/H2 自动配置 | 根据当前 DataSource 自动选择数据库插件，提供方言和监控实现 |
| `gyyun-service` | `ServiceConfiguration` 扫描 `com.gyyun.ds.service` | 提供 workflow、command、cron、alert 等业务编排服务 |
| `gyyun-meter` | `MeterAutoConfiguration` 创建 `DefaultMetricsProvider`、`TimedAspect`、`CountedAspect` | 采集系统指标、JVM 指标、Micrometer 计数和耗时 |
| `gyyun-authentication` | `ActuatorAuthenticationAutoConfiguration` 创建 actuator 安全过滤器 | 控制 `/actuator` 与 `/gyyun/actuator` 的访问权限 |
| `gyyun-storage-plugin` | `StorageConfiguration` 读取 `resource.storage.type`，用 SPI 创建 `StorageOperator` | 给资源中心、日志、迁移工具提供本地/HDFS/S3/OSS 等存储能力 |

这些动作的共同作用是把运行时基础设施准备好。服务自己的 `@PostConstruct` 再基于这些 Bean 启动 RPC、注册中心、调度器和后台循环。

## 3. API Server

入口：

```text
gyyun-api/src/main/java/com/gyyun/ds/api/ApiApplicationServer.java
```

### 3.1 启动时动作

```text
ApiApplicationServer.main()
  -> ApiServerMetrics.registerUncachedException(...)
  -> Thread.setDefaultUncaughtExceptionHandler(...)
  -> SpringApplication.run(ApiApplicationServer.class)
  -> 导入 DaoConfiguration / CommonConfiguration / ServiceConfiguration / StorageConfiguration / RegistryConfiguration
  -> 启动 Jetty 与 Spring MVC
  -> AppConfiguration 创建 CORS、Locale、限流、登录拦截器、静态资源映射
  -> UiPluginServiceImpl.@PostConstruct 读取 t_ds_version
  -> PythonGateway.@PostConstruct 按配置决定是否启动 Py4J Gateway
  -> ApplicationReadyEvent
       -> ServerLifeCycleManager.toRunning()
       -> DataSourcePluginManager.loadDataSourcePlugin()
       -> TaskPluginManager.loadTaskPlugin()
```

各动作作用：

| 动作 | 作用 |
| --- | --- |
| 注册未捕获异常指标与默认异常处理器 | 把线程级异常纳入 API 指标，避免异常静默 |
| 导入 DAO/Common/Service/Storage/Registry | 让 Controller 和 Service 可以访问元数据库、注册中心和资源存储 |
| 启动 Jetty/Spring MVC | 提供 `/gyyun/` 下 REST API 和 UI 静态资源访问 |
| 创建 `CorsFilter` | 允许 UI 或外部系统跨域调用 API |
| 创建 `LocaleChangeInterceptor` | 根据请求头/cookie 选择 i18n 语言 |
| 创建 `RateLimitInterceptor` | 配置开启时限制全局或租户 QPS |
| 创建 `LoginHandlerInterceptor` | 校验 session/token，过滤未登录请求 |
| `UiPluginServiceImpl.init()` | 缓存产品版本，供 UI 查询产品信息 |
| `PythonGateway.init()` | 配置开启时启动 Py4J，供 Python API 反调 Java 服务 |
| `ApplicationReadyEvent` 加载任务/数据源插件 | 让 API 能校验任务参数、展示任务类型、测试数据源连接 |

注意：API 的 `application.yaml` 中 `spring.quartz.auto-startup: false`，因此 API 自身不会启动 Quartz 调度线程。

### 3.2 启动后动作

API 启动后主要是被 HTTP 请求驱动：

```text
浏览器 / SDK / curl
  -> Jetty
  -> Spring MVC
  -> CORS / Locale / RateLimit / LoginInterceptor
  -> Controller
  -> Service
  -> DAO / Storage / Registry / RPC Client
  -> Result JSON
```

典型启动后数据流：

| 数据流 | 动作 | 作用 |
| --- | --- | --- |
| 登录/鉴权 | `LoginController`、`LoginHandlerInterceptor`、`SecurityConfig` | 建立会话或 token，保护后续业务接口 |
| 工作流定义维护 | Controller/Service 写 `t_ds_workflow_definition`、`t_ds_task_definition`、关系表 | 保存 DAG 定义和任务参数 |
| 手动启动工作流 | API 查询注册中心中的 Master，RPC 调 `IWorkflowControlClient` | 把用户操作转为 Master 可执行的 workflow command |
| 调度上线/下线 | API 调 `SchedulerApi.insertOrUpdateScheduleTask/deleteScheduleTask` | 写 Quartz job/trigger，使定时任务后续由 Master Quartz 触发 |
| 资源中心 | API 调 `StorageOperator` 与 DAO | 上传、下载、查询资源文件，并维护元数据 |
| 日志查询 | API 通过 Registry/RPC 找 Master 或 Worker 的 `ILogService` | 拉取任务运行日志或应用 ID |
| 告警测试 | API 查 Alert Server 地址，RPC 调 `IAlertOperator.sendTestAlert` | 测试告警插件实例参数是否可用 |
| 监控查询 | API 读 Registry 心跳和 Meter 指标 | 展示 Master/Worker/Alert 活跃状态与资源使用 |

## 4. Master Server

入口：

```text
gyyun-master/src/main/java/com/gyyun/ds/server/master/MasterServer.java
```

Master 是启动动作最多的模块。

### 4.1 启动时动作

```text
MasterServer.main()
  -> 注册 Master 未捕获异常指标
  -> 设置默认异常处理器
  -> 设置当前线程名 MasterServer
  -> SpringApplication.run(MasterServer.class)
  -> @PostConstruct MasterServer.initialized()
       -> ServerLifeCycleManager.toRunning()
       -> MasterRpcServer.start()
       -> TaskPluginManager.loadTaskPlugin()
       -> DataSourcePluginManager.loadDataSourcePlugin()
       -> MasterRegistryClient.start()
       -> masterRegistryClient.setRegistryStoppable(this)
       -> MasterCoordinator.start()
       -> ClusterManager.start()
       -> ClusterStateMonitors.start()
       -> WorkflowEngine.start()
       -> SchedulerApi.start()
       -> SystemEventBus.publish(GlobalMasterFailoverEvent)
       -> SystemEventBusFireWorker.start()
       -> 注册 CPU / 内存 metrics
       -> 注册 shutdown hook
```

各动作作用：

| 动作 | 作用 |
| --- | --- |
| `MasterRpcServer.start()` | 启动 Netty RPC，监听 `master.listen-port`，接收 API、Quartz、Worker、逻辑任务回调 |
| `TaskPluginManager.loadTaskPlugin()` | 通过 SPI 加载所有任务类型，供参数解析和逻辑任务/物理任务创建使用 |
| `DataSourcePluginManager.loadDataSourcePlugin()` | 加载数据源插件，供 SQL、Hive、Spark 等任务构造连接信息 |
| `MasterRegistryClient.start()` | 写 `/masters/{host:port}` 临时节点，启动 Master 心跳线程 |
| `setRegistryStoppable(this)` | 注册中心发现自己被 failover 标记时可以主动停止当前进程 |
| `MasterCoordinator.start()` | 基于注册中心选出 active coordinator，只有 active 执行 task group、串行工作流协调和 failover 清理 |
| `ClusterManager.start()` | 初始加载 Master/Worker 列表，并订阅注册中心节点变化 |
| `ClusterStateMonitors.start()` | 监听 Master/Worker 下线，发布延迟 failover 系统事件 |
| `WorkflowEngine.start()` | 启动命令消费、工作流事件总线、任务分发、本地逻辑任务引擎 |
| `SchedulerApi.start()` | 启动 Quartz 调度器，让在线调度可以触发工作流 |
| 发布 `GlobalMasterFailoverEvent` | 启动后检查历史未完成工作流/任务，处理 Master 全局恢复 |
| `SystemEventBusFireWorker.start()` | 消费系统事件，例如全局 failover、Master failover、Worker failover |
| 注册 metrics | 暴露 Master CPU、内存、异常、命令消费、心跳等指标 |

### 4.2 MasterRegistryClient 和心跳

```text
MasterRegistryClient.start()
  -> new MasterHeartBeatTask(...)
  -> registry()
       -> registryClient.remove(masterRegistryPath)
       -> registryClient.persistEphemeral(masterRegistryPath, firstHeartBeatJson)
       -> 等待注册中心确认节点存在
       -> MasterHeartBeatTask.start()
  -> registryClient.addConnectionStateListener(...)
```

`MasterHeartBeatTask` 每秒扫描一次，达到 `master.max-heartbeat-interval` 或服务状态变化时写心跳。心跳包含：

```text
startupTime / reportTime / processId
host / port
cpuUsage / jvmCpuUsage / memoryUsage / diskUsage
serverStatus: NORMAL 或 BUSY
isCoordinator: 当前 Master 是否 active coordinator
```

作用：

- 让 API、其他 Master、监控页面知道 Master 是否在线。
- 让 Master 集群计算 slot，避免多个 Master 重复消费同一批 command。
- overload 时把状态写成 `BUSY`，让调度和负载保护可以避开高负载节点。
- 如果发现 failover finished 节点中已有当前 Master，说明它已被其他节点接管，会主动停止自己。

### 4.3 MasterCoordinator

`MasterCoordinator` 继承 `AbstractHAServer`，通过注册中心路径和分布式锁选 active。

```text
MasterCoordinator.start()
  -> AbstractHAServer.start()
       -> subscribe(coordinatorPath)
       -> participateElection()
       -> active 或 standby

changeToActive()
  -> TaskGroupCoordinator.start()
  -> WorkflowSerialCoordinator.start()
  -> 每天清理历史 failover finished 标记

changeToStandBy()
  -> TaskGroupCoordinator.close()
  -> WorkflowSerialCoordinator.close()
  -> 取消定时清理任务
```

作用：

- 避免所有 Master 同时修改 task group 队列、串行工作流队列等全局资源。
- active coordinator 负责需要集群唯一执行的协调任务。
- standby Master 仍可消费属于自己 slot 的 command，但不执行全局 coordinator 任务。

### 4.4 ClusterManager 和 failover 监听

```text
ClusterManager.start()
  -> initializeMasterClusters()
       -> 读 RegistryNodeType.MASTER 当前节点
       -> 注册 MasterSlotChangeListener
       -> subscribe /masters
  -> initializeWorkerClusters()
       -> 读 RegistryNodeType.WORKER 当前节点
       -> subscribe /workers
       -> WorkerGroupChangeNotifier.start()

ClusterStateMonitors.start()
  -> 注册 masterRemoved 监听
  -> 注册 workerRemoved 监听
```

作用：

- Master 内存中维护实时 Master/Worker 列表。
- Worker 心跳变化会影响任务分发时的可选 Worker 和负载权重。
- Master 节点变化会触发 slot 重新分配，使 command 消费范围变化。
- 节点下线会向 `SystemEventBus` 发布延迟 30 秒的 failover 事件；如果节点很快重连，可避免误切。

### 4.5 WorkflowEngine 启动后常驻动作

```text
WorkflowEngine.start()
  -> WorkflowEventBusCoordinator.start()
       -> WorkflowEventBusFireWorkers.start()
  -> CommandEngine.start()
  -> WorkerGroupDispatcherCoordinator.start()
  -> LogicTaskEngineDelegator.start()
```

#### 4.5.1 CommandEngine

`CommandEngine` 是 `MasterCommandLoopThread`。

```text
while running:
  -> 读取系统指标
  -> 如果 Master overload，暂停消费 command
  -> commandFetcher.fetchCommands()
  -> 每条 command 放入 commandHandleThreadPool
       -> WorkflowExecutionFactory.createWorkflowExecuteRunnable(command)
       -> workflowRepository.put(workflowExecution)
       -> workflowEventBusCoordinator.registerWorkflowEventBus(workflowExecution)
       -> workflowEventBus.publish(WorkflowStartLifecycleEvent)
       -> 成功则增加 consume command 指标
       -> 失败则把 workflowInstance 置失败，并 moveToErrorCommand
```

作用：

- 把 DB 中的 `t_ds_command` 转为内存里的 `WorkflowExecution`。
- 将“请求启动工作流”转为“事件驱动的 DAG 状态机”。
- 用 command fetch strategy 和 Master slot 防止多 Master 重复消费。

#### 4.5.2 WorkflowEventBusFireWorkers

```text
WorkflowEventBusFireWorkers.start()
  -> 创建 N 个 WorkflowEventBusFireWorker
  -> 注册所有 ILifecycleEventHandler
  -> 每 100ms scheduleWithFixedDelay(fireAllRegisteredEvent)
```

启动后，每个 fire worker 会处理自己 slot 中已注册工作流的事件：

```text
WorkflowStartLifecycleEvent
  -> WorkflowStartLifecycleEventHandler
  -> 创建/更新 workflow instance 状态
  -> 找到可运行 task
  -> 发布 TaskStartLifecycleEvent
  -> 创建 task instance / task execution context
  -> 发布 TaskDispatchLifecycleEvent
  -> WorkerGroupDispatcher 分发到逻辑任务或物理 Worker
```

作用：

- 统一驱动工作流和任务生命周期。
- 将任务成功/失败/暂停/超时等事件转成 DB 状态更新和后继 DAG 推进。
- DB 连接异常时会把事件放回队列重试，避免状态机丢事件。

#### 4.5.3 WorkerGroupDispatcherCoordinator

`WorkerGroupDispatcherCoordinator.start()` 本身只记录启动；真正的 `WorkerGroupDispatcher` 在首次向某个 worker group 分发任务时创建。

```text
dispatchTask(taskExecution, delay)
  -> getOrCreateWorkerGroupDispatcher(workerGroup)
       -> new WorkerGroupDispatcher(...)
       -> workerGroupDispatcher.start()
  -> 放入延迟优先队列

WorkerGroupDispatcher.run()
  -> take() 等待可分发任务
  -> taskExecutorClient.dispatch(taskExecution)
  -> 分发失败则按失败次数延迟重试
  -> 超过 dispatch timeout 则发布 TaskFailedLifecycleEvent
```

作用：

- 按 worker group 隔离分发队列。
- 支持延迟重试，避免 Worker 短暂不可用导致任务直接失败。
- 结合 Worker 心跳中的状态、权重和线程池使用率选择目标 Worker。

#### 4.5.4 LogicTaskEngineDelegator

Master 内部有一些不需要 Worker 执行的逻辑任务，例如 condition、switch、dependent、subworkflow。

```text
LogicTaskEngineDelegator.start()
  -> TaskEngine.start()
       -> TaskExecutorEventBusCoordinator.start()
  -> LogicTaskExecutorLifecycleEventReporter.start()
```

作用：

- 在 Master 本地执行逻辑任务。
- 将逻辑任务生命周期事件重新上报给 Master 任务状态机，保持和 Worker 物理任务同一套事件模型。

### 4.6 Quartz 启动后动作

Master 启动 `SchedulerApi.start()` 后，Quartz 开始工作。

```text
QuartzScheduler.start()
  -> scheduler.start()

Quartz trigger fire
  -> ProcessScheduleTask.executeInternal(...)
       -> 查询 t_ds_schedules
       -> 查询 t_ds_workflow_definition
       -> 如果 schedule 或 workflow 已下线，则删除 Quartz job
       -> 构造 WorkflowScheduleTriggerRequest
       -> IWorkflowControlClient.scheduleTriggerWorkflow(...)
```

作用：

- 将“定时触发”转化为一次工作流触发请求。
- 后续仍会落到 Master 的 command/WorkflowEventBus 主流程。
- 失效调度会自动清理，避免 Quartz 持续触发不存在或下线的 workflow。

### 4.7 SystemEventBusFireWorker

```text
SystemEventBusFireWorker.start()
  -> while flag:
       -> systemEventBus.take()
       -> 找到匹配 ISystemEventHandler
       -> handler.handle(event)
       -> 失败则重新 publish 并 10s 后重试
```

作用：

- 处理 `GlobalMasterFailoverEvent`、`MasterFailoverEvent`、`WorkerFailoverEvent`。
- 对启动前遗留的 RUNNING 工作流/任务做恢复。
- 对下线 Master 或 Worker 上的未完成任务做迁移、失败或重试处理。

## 5. Worker Server

入口：

```text
gyyun-worker/src/main/java/com/gyyun/ds/server/worker/WorkerServer.java
```

### 5.1 启动时动作

```text
WorkerServer.main()
  -> 注册 Worker 未捕获异常指标
  -> 设置默认异常处理器
  -> 设置当前线程名 WorkerServer
  -> SpringApplication.run(WorkerServer.class)
  -> WorkerRegistryClient.@PostConstruct
       -> 创建 WorkerHeartBeatTask
  -> @PostConstruct WorkerServer.run()
       -> ServerLifeCycleManager.toRunning()
       -> WorkerRpcServer.start()
       -> TaskPluginManager.loadTaskPlugin()
       -> DataSourcePluginManager.loadDataSourcePlugin()
       -> WorkerRegistryClient.setRegistryStoppable(this)
       -> WorkerRegistryClient.start()
       -> PhysicalTaskEngineDelegator.start()
       -> 注册 CPU / 内存 metrics
       -> 注册 shutdown hook
```

各动作作用：

| 动作 | 作用 |
| --- | --- |
| `WorkerRpcServer.start()` | 启动 Netty RPC，接收 Master 的任务下发、kill、pause、查询、ACK |
| 加载任务插件 | Worker 创建具体 `AbstractTask` 时需要任务插件 |
| 加载数据源插件 | SQL/Hive/Spark 等任务执行时需要外部数据源能力 |
| `WorkerRegistryClient.start()` | 写 `/workers/{host:port}` 临时节点并启动心跳 |
| `PhysicalTaskEngineDelegator.start()` | 启动物理任务事件总线和远程生命周期上报线程 |
| 注册 metrics | 暴露 Worker CPU、内存、心跳、异常等指标 |

### 5.2 WorkerRegistryClient 和心跳

```text
WorkerRegistryClient.start()
  -> registry()
       -> registryClient.remove(workerRegistryPath)
       -> registryClient.persistEphemeral(workerRegistryPath, firstHeartBeatJson)
       -> 等待注册中心确认节点存在
       -> WorkerHeartBeatTask.start()
  -> registryClient.addConnectionStateListener(...)
```

`WorkerHeartBeatTask` 写入：

```text
startupTime / reportTime / processId
host / port / workerGroup / workerHostWeight
cpuUsage / jvmCpuUsage / memoryUsage / diskUsage
threadPoolUsage
serverStatus: NORMAL 或 BUSY
```

作用：

- 让 Master 发现 Worker RPC 地址。
- 让 Master 按 worker group 过滤可用 Worker。
- 让动态加权负载均衡根据 CPU、内存、线程池使用率选择 Worker。
- 如果 Worker 已被 failover 标记，主动 stop，避免旧进程继续执行已被接管的任务。

### 5.3 启动后任务执行动作

Master 下发任务时：

```text
Master
  -> IPhysicalTaskExecutorOperator.dispatchTask(TaskExecutorDispatchRequest)
  -> Worker PhysicalTaskExecutorOperatorImpl.dispatchTask(...)
  -> PhysicalTaskEngineDelegator.dispatchLogicTask(taskExecutionContext)
  -> PhysicalTaskExecutorFactory.createTaskExecutor(...)
  -> TaskEngine.submitTask(taskExecutor)
       -> executorContainer.dispatch(taskExecutor)
       -> taskExecutorRepository.put(taskExecutor)
       -> publish TaskExecutorDispatchedLifecycleEvent
       -> executorContainer.start(taskExecutor)
```

`TaskEngine.start()` 已经启动 `TaskExecutorEventBusCoordinator`：

```text
每 50ms:
  -> 扫描 taskExecutorRepository
  -> 取每个 executor 的事件
  -> 调用所有 ITaskExecutorLifecycleEventListener
```

Worker 侧事件流：

```text
DISPATCHED
  -> TaskExecutorWorker.start()
  -> RUNNING
  -> 插件 AbstractTask.handle(...)
  -> RUNTIME_CONTEXT_CHANGE 若运行上下文变化
  -> SUCCESS / FAILED / KILLED / PAUSED
  -> PhysicalTaskExecutorLifecycleEventReporter 远程上报 Master
  -> Master ACK
  -> Worker 收到终态 ACK
  -> FINALIZE
  -> 移除执行器、释放执行槽、远程日志上传、清理资源
```

作用：

- Worker 不直接推进 DAG，不直接作为任务最终状态写库主入口。
- Worker 用生命周期事件告诉 Master 任务发生了什么。
- Master 收到事件后更新 `t_ds_task_instance`，再推动后继任务或结束工作流。

### 5.4 启动后控制动作

Worker RPC 还会处理：

| RPC | 启动后动作 | 作用 |
| --- | --- | --- |
| `killTask` | 发布 `TaskExecutorKillLifecycleEvent` | 中止任务插件或外部应用 |
| `pauseTask` | 发布 `TaskExecutorPauseLifecycleEvent` | 暂停可暂停任务 |
| `reassignWorkflowInstanceHost` | 修改执行上下文中的 Master host 并通知 reporter | Master failover 后让 Worker 后续事件发往新 Master |
| `ackPhysicalTaskExecutorLifecycleEvent` | reporter 移除已被 Master 确认的事件 | 保证事件上报至少一次，并在 ACK 后清理 |
| 日志查询接口 | 读取本地或远程日志 | 给 API/UI 展示任务日志 |
| savepoint 接口 | 触发流式任务 savepoint | 控制 Flink 等流任务运行状态 |

```text

  -> new AlertHeartbeatTask(...)
  -> AlertHeartbeatTask.start()

AlertHeartbeatTask.writeHeartBeat(...)
  -> registryClient.persistEphemeral(/alert-server/{address}, heartBeatJson)
```

心跳包含：

```text

host / port
cpuUsage / memoryUsage / diskUsage
isActive
serverStatus
```

`AlertHAServer` 继承 `AbstractHAServer`：

```text
participateElection()
  -> 获取 selectorPath-lock
  -> 如果 leader path 不存在则写入自己
  -> 如果 leader path 是自己则 active
  -> 否则 standby
```

作用：

- 多个 Alert Server 可以同时在线。
- 只有 active 节点消费 `t_ds_alert`，避免重复发送异步告警。
- 所有节点都可以暴露 RPC；同步测试告警只要打到可用节点即可。

### 6.3 启动后动作

active 后：

```text
changeToActive()
  -> AlertBootstrapService.start()
       -> AlertEventFetcher.start()
       -> AlertEventLoop.start()
```

`AlertEventFetcher`：

```text
while running:
  -> 如果当前节点不是 active，sleep 5s
  -> alertDao.listPendingAlerts(eventOffset)
  -> 放入 AlertEventPendingQueue
  -> 更新 eventOffset
```

`AlertEventLoop`：

```text
while running:
  -> 如果处理线程已满，sleep 1s
  -> eventPendingQueue.take()
  -> CompletableFuture.runAsync(handleEvent, alertSenderThreadPool)
```

`AlertSender`：

```text
Alert
  -> 查询 alert group 绑定的 AlertPluginInstance
  -> 按 pluginDefineId 找 AlertChannel
  -> 组装 AlertInfo
  -> AlertChannel.process(...)
  -> 根据全部成功/部分成功/失败回写 t_ds_alert
```

作用：

- `t_ds_alert` 是可靠性来源，内存队列只负责 active 节点本轮处理。
- 告警插件负责真正发送，例如 email、HTTP、飞书、钉钉等。
- 发送结果写回数据库，UI 可以查询告警状态和日志。

同步/测试告警 RPC：

```text
IAlertOperator.sendAlert(...)
  -> AlertSender.syncHandler(...)
  -> 直接调用插件发送
  -> 返回 AlertSendResponse

IAlertOperator.sendTestAlert(...)
  -> AlertSender.syncTestSend(...)
  -> 不落 t_ds_alert
  -> 返回测试结果
```

## 11. Task Executor 模块

`gyyun-task-executor` 是 Master 逻辑任务和 Worker 物理任务共用的生命周期框架。

启动时：

```text
LogicTaskEngineDelegator.start() 或 PhysicalTaskEngineDelegator.start()
  -> TaskEngine.start()
       -> TaskExecutorEventBusCoordinator.start()
            -> 每 50ms 扫描 executor 事件
  -> TaskExecutorLifecycleEventRemoteReporter.start()
```

启动后：

```text
TaskEngine.submitTask(executor)
  -> executorContainer.dispatch(executor)
  -> repository.put(executor)
  -> publish DISPATCHED
  -> executorContainer.start(executor)

TaskExecutorEventBusCoordinator
  -> 触发 listener
  -> listener 调用 executor.start/kill/pause/finalize 或 reporter.report

TaskExecutorLifecycleEventRemoteReporter
  -> 按 taskInstanceId 缓存待上报事件
  -> 周期性发送给 Master
  -> 收到 ACK 后移除
  -> 终态 ACK 后发布 FINALIZE
```

作用：

- 把任务执行过程抽象成统一生命周期事件。
- 让 Master 本地逻辑任务和 Worker 物理任务用同一套状态语义。
- 通过 ACK 和重试保证 Worker/逻辑任务事件不会轻易丢失。

## 15. 端到端启动后主数据流

系统全部启动后，一次工作流运行大致是：

```text
1. 用户在 UI 点击运行
   -> API Controller
   -> 登录/权限/参数校验
   -> API 通过 Registry 找 Master
   -> RPC: IWorkflowControlClient.manualTriggerWorkflow

2. Master 接收触发
   -> 创建 workflow instance
   -> 写 t_ds_command 或 t_ds_serial_command

3. CommandEngine 常驻消费
   -> fetch t_ds_command
   -> 创建 WorkflowExecution
   -> 注册 WorkflowEventBus
   -> 发布 WorkflowStartLifecycleEvent

4. WorkflowEventBusFireWorkers 推进 DAG
   -> 创建 task instance
   -> 构造 TaskExecutionContext
   -> 发布 TaskDispatchLifecycleEvent

5. 任务分发
   -> WorkerGroupDispatcher
   -> 根据 worker group 和负载选择 Worker
   -> RPC: IPhysicalTaskExecutorOperator.dispatchTask

6. Worker 执行
   -> PhysicalTaskExecutorFactory
   -> TaskEngine.submitTask
   -> TaskPluginManager 创建具体任务
   -> AbstractTask.handle
   -> 发布 SUCCESS / FAILED / KILLED / PAUSED

7. Worker 回传 Master
   -> PhysicalTaskExecutorLifecycleEventReporter
   -> RPC: ITaskExecutorEventListener
   -> Master ACK
   -> Worker FINALIZE 清理

8. Master 继续推进
   -> 更新 t_ds_task_instance
   -> 触发后继任务或结束 workflow
   -> 更新 t_ds_workflow_instance
   -> 需要时写 t_ds_alert

9. Alert active 节点处理
   -> AlertEventFetcher 轮询 t_ds_alert
   -> AlertEventLoop 并发发送
   -> AlertChannel.process
   -> 回写告警状态
```

## 16. 启动顺序建议

生产环境建议：

```text
1. 元数据库
2. 注册中心：ZooKeeper / Etcd / JDBC registry 依赖的数据库
3. gyyun-tools 数据库初始化/升级
4. Alert Server
5. Worker Server
6. Master Server
7. API Server
8. UI 或访问 API 内置 /ui
```

原因：

- DAO 和 Registry 是所有服务的基础依赖。
- Tools 先建表，避免插件注册、心跳、调度启动时表不存在。
- Worker 先于 Master 启动可以让 Master 初始集群视图直接看到 Worker。
- Alert 先启动可以让后续工作流失败告警有可用消费端。
- API 最后启动可以避免用户过早触发工作流但 Master/Worker 尚未就绪。

## 17. 关闭时反向动作

几个常驻服务都有 shutdown hook 或 `@PreDestroy`：

| 服务 | 关闭动作 | 作用 |
| --- | --- | --- |
| Master | `ServerLifeCycleManager.toStopped()`，停止调度线程、系统事件、WorkflowEngine、Quartz、RPC、Registry、SpringContext | 停止消费 command 和事件，删除/关闭注册中心连接，释放资源 |
| Worker | 停止物理任务引擎、RPC、WorkerRegistryClient、心跳 | 停止接收新任务，释放执行槽和注册中心节点 |
| Alert | 停止 RPC、Registry、HAServer、AlertBootstrapService | standby/销毁时停止异步告警消费，避免重复发送 |
| Quartz | `scheduler.shutdown()` | 停止 cron trigger |
| Registry | `close()` | 关闭 Curator/Etcd/JDBC registry client，释放 watch 和锁 |

关闭动作的目标是让注册中心节点消失或停止更新，使其他节点能通过订阅事件触发 failover 或重新选择可用节点。
